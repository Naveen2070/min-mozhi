## Round 6 plan — Task 4 (BUG-63) real fix, function-local `reg`-based hoisting

Continuation of [`2026-08-15.md`](2026-08-15.md)'s Tasks 1–3. Task 4
(`docs/plan/v0.2-class-closure-round6.local.md`) previously only diagnosed a
`fn`-body hoist (`in_fn_body` guard, `Diag` instead of invalid Verilog); this
session implements the real fix.

**What changed.** `Emitter` gained a `fn`-local hoist buffer —
`fn_hoist_counter`/`fn_hoisted_regs`/`fn_hoisted_stmts` — entirely separate
from the module's own `hoist_counter`/`hoisted_decls`, saved/restored by
`render_fn_decl` alongside `cur_decls`/`in_fn_body`. `hoist_if_needed` and
`hoist_slice_base_if_needed`, when `self.in_fn_body`, now push a
`reg [W-1:0] __mimz_fn_sub_N;` line and a `__mimz_fn_sub_N = <expr>;`
statement into that buffer and return the name, instead of pushing a `Diag`.

A new `render_fn_operand` helper (`emit_verilog/module/funcs.rs`) wraps every
`expr_subst` call `render_fn_decl`/`emit_fn_stmts` makes for a statement's own
operand (tail, `let` value — including each array-literal element, `return`
value, `if` condition): it drains `fn_hoisted_stmts` right after rendering and
returns a correctly-indented prefix, which the caller splices in immediately
before that statement's own line — so a hoisted assignment lands in the right
control-flow branch and runs before its use, matching a `function automatic`'s
sequential-execution requirement. `fn_hoisted_regs` (the `reg` declarations)
is spliced into the function body at a saved position (`regs_pos`, captured
right before `begin`) only after the whole body has rendered, since Verilog-
2005 requires every `reg` declared before the function's first statement but
a hoist is only discovered mid-render — same `insert_str`-at-saved-position
trick `module()` and yesterday's testbench-flush fix both already use, one
level down.

## Round 6 plan — Task 5 (BUG-64) fixed, second bug (BUG-65) found and fixed in the same task

Task 5's own plan named one race (`Drive` non-blocking, no settle before a
following `Expect` in a clocked-free test) and three repro examples
(`enum_encoding`, `shift`, `tested_adder`). Landing it for real found two
more things the plan didn't name.

**The race itself was two races, not one.** `emit_verilog/testbench.rs`'s
`TestStmt::Drive` AND `TestStmt::Tick` now both emit an unconditional `#1;`
right after their own statement:

- `Drive` with no following `Tick` (the plan's own shape) — `shift`/
  `tested_adder`, plus half of `enum_encoding`'s (`rst <= 0;` immediately
  followed by an `expect`, inside a test that ticks elsewhere).
- `Tick` immediately followed by a read (found verifying the first fix,
  not in the plan): `repeat (n) @(posedge clk)` resumes in the SAME active
  region as the DUT's own `always @(posedge clk)` firing for that identical
  edge — the NBA from that edge never lands until the active region is
  entirely done, so a read right after `Tick` resumes deterministically sees
  the pre-edge value. `enum_encoding`'s other `tick(clk); expect …` pairs
  needed this too. First attempt gated both `#1`s on "does this whole test
  ever tick a clock" (`test_is_combinational`) — reverted once this second
  race showed a test WITH ticks elsewhere still needs the delay at each
  individual site, not once for the whole test.

**Running the sweep the plan called for, for the first time, found BUG-65** —
`docs/audit/bugs/bug-61-70.md`. `every_emitted_testbench_reports_pass_under_
vvp` (new, `tests/icarus.rs`) had never existed before; running it after the
race fixes above found 50 more FAILs, unrelated, across `debouncer`/`fifo`/
`pwm`/`uart_tx` × 5 language variants. Root cause: `ModuleItem::Reg`'s own
doc comment states the same "no uninitialized state" rule `mem`'s does, and
`mimz-sim`'s own kernel test (`regs_init_to_their_reset_value`) confirms a
reg holds its declared value from t=0 unconditionally — but the emitter only
ever encoded that value into the synchronous `if (rst)` path, never as a
Verilog `initial` the way `mem` already gets. Checked the kernel's intent
before picking a fix (user-directed mid-task, between patching the 20
example test files vs. extending the emitter): the kernel's test is
deliberate, spec/01 agrees ("every reg declares a reset value; a module with
regs must declare a reset"), so the fix extends `mem`'s own `initial`
mechanism to plain `reg` (`module/mod.rs`), unchanged example sources.

A third fix rode along inside BUG-65's own: the new `initial <reg> = …;` in
the DUT races the testbench's OWN `initial begin … end` (different `initial`
constructs starting at time 0 have no ordering guarantee between each
other) — a test with no `Drive`/`Tick` before its first `Expect` (`fifo`'s
"starts empty", `uart_tx`'s "idles high") could check before the DUT's own
reg-init ran. One more unconditional `#1;` at the very start of the
testbench's `initial` block, before the first user statement, closes it.

**A wording constraint worth remembering:** `pure_tamil_examples_are_
equivalent_to_their_counterparts` canonicalizes every non-keyword word-token
(comments included) to `id<N>` in first-occurrence order, to compare a Tamil
example against its English counterpart. BUG-65's comment first used "state"
and "value" — both collided with real reg names in `blinker.mimz`/
`counter.mimz`, breaking the equivalence check for those two pairs only.
Final wording avoids common single-word nouns.
