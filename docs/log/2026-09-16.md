## Investigated: "OR-mux `??` against a bundle-typed fn tail" residual — re-scoped, not fixed

- Asked to fix yesterday's flagged residual (`docs/audit/gaps.md`, the
  `??`-against-a-bare-bundle-param sub-gap's OR-mux-form leftover).
- Probed empirically (two throwaway tests, not committed) before writing
  code: a bundle-returning `fn` call with **zero** `??` involved
  (`fn make_handshake(v: bit) -> Handshake(W: 8) { { valid: v, data: 0 } }`)
  panics at the exact same site (`ir::lower`'s generic `Field`-not-yet-
  lowered catch-all) as the `??`/OR-mux shape does.
- Conclusion: this was never a Coalesce-specific gap. Bundle-typed `fn`-call
  RESULTS are entirely unlowerable in `ir::lower` today — `bundle_field_expr`
  never inlines a callee to extract one field, and `ir::lower`'s `FnCall`
  arm only ever produces one flat `Bits` for a whole call, with no
  per-field slicing. Yesterday's "OR-mux fn TAIL" framing was too narrow;
  corrected in place in `docs/audit/gaps.md`.
- Real fix needs a Decision (which layer inlines a bundle-typed fn call:
  elaborate's `bundle_field_expr`, or a new `ir::lower` `Field` handler) —
  same weight class as the two 2026-09-10 IR Decisions (signed `Bits`,
  loop unrolling). Not attempted here; no code changed today, `gaps.md`
  only.
