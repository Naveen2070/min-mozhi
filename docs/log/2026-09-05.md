## IR: `Shl` sizes exactly for a compile-time-constant shift amount (GAP-1 residual, task 1 of 6)

Follow-up to the 2026-09-04 GAP-1 fix round's own residual note: fixing
`Shl`'s truncation bug that day made `ir::lower` size `out` at worst-case
growth unconditionally, which is always safe but strictly wider than the
checker's own exact `a.width() + k` formula whenever the shift amount is a
compile-time constant — leaving `(a << 2) & c` failing `ir::validate` with a
`WidthMismatch` even though both sides type-check individually.

`lower_binop` gained a `shl_const_amount: Option<u128>` parameter (only
meaningful for `BinOp::Shl`). Its one call site (`ExprKind::Binary` in
`lower_expr`) const-evals the source `rhs` `Expr` via `crate::value::
const_eval` against `design.consts` when `op == BinOp::Shl`, converting a
successful non-negative result to `u128` (`try_from`, falling back to `None`
rather than panicking on the never-expected negative/overflow case) — the
same resolution `checker/widths/ops/mod.rs::shift_ty` and `value/binary.rs::
eval_shift_chain` already use. A genuinely runtime shift amount still passes
`None` and keeps the worst-case fallback unchanged (pinned by the existing
`shl_grows_the_output_to_the_worst_case_width_not_the_input_width` test,
untouched).

`ir::validate`'s independent `Shl` width formula (`expected_widths`) was
still hardcoded to `None` and would have started disagreeing with
`lower_binop`'s new exact sizing the moment a constant-shift program was
lowered — caught by actually running the new fixture before assuming the
brief's file list was complete. Added `shl_const_amount(module, driver, b)`:
when `b` is driven entirely by one `Const` cell (the shape `ir::lower`
produces for a literal/const-name shift amount), it reads that cell's value
back and passes it through the same `width_rules::shift_result` call, so the
two independently-computed formulas agree again. Anything else (a runtime
`b`, a constant reached only indirectly, or one too wide for `u128`) falls
back to `None` — the safe/wide side.

Corrected the stale `lower_binop`/`Shl`-arm comment and doc comments in
`ir/exec.rs`'s "v1 limitations" list that both claimed `lower_binop` "cannot
know" or has no access to the compile-time-constant fact — no longer true.

New tests (+2, both `crates/mimz-core/src/ir/tests/lower_binops.rs`):
`shl_with_a_compile_time_constant_amount_sizes_exactly_not_worst_case`
(`a: bits[2] << 2` sizes `y` at 4 bits, not the worst-case 5) and
`shl_result_feeding_a_matched_width_cell_validates_cleanly_when_amount_is_constant`
(`(a << 2) & c`, the exact repro from the gaps.md residual, now validates
clean). Test count 1404 → 1406 in `docs/code/10-test-map.md` and the README
badge (lib-unit row 832 → 834).

`docs/audit/gaps.md`: marked the "Narrower than originally scoped" paragraph
under GAP-1's `<<`/`>>` sub-gap RESOLVED. Left the sibling "silent-over-wide
port" and "checker-legal program can panic in lowering" paragraphs, and the
still-open fused-shift-chain issue, untouched — those are separate, later
follow-ups.

## IR: `ir::Module` records each output port's declared width; `validate` catches a silent over-wide port (GAP-1 residual, task 2 of 6)

Closes the sibling residual this same GAP-1 sub-gap left open: an over-wide
`Shl` result reaching a module OUTPUT PORT directly — or via `extend`'s
`target <= base.width()` no-op branch, e.g. `out y: bits[10] = extend(a <<
sh, 10)` when `sh` is a genuinely runtime shift amount — used to give `y`
more real nets than the source declared, with nothing in `validate()`
reporting it, because `ir::Module` carried no record of a port's
originally-declared width once lowering was done.

`ir::Module` gained `port_declared_widths: BTreeMap<String, u32>`, following
the exact `extern_decls`/`signals` precedent: populated by `lower()` from
`design.outputs`'s own `Signal.width.bits` in the existing `design.outputs`
loop, not round-tripped by the text format (`parse_line`/`print_line` don't
touch it), so a hand-parsed IR module has no declared width on record and
`validate` skips the new check gracefully rather than treating a missing
entry as a violation — same pattern as the black-box-port-shape check.
`validate()` gained its sixth check (module doc comment updated from "Five
checks" to "Six checks"): for every OUTPUT-direction port with a
`port_declared_widths` entry, compare it against the port's actual lowered
`Bits::width()` and report a new `ValidationError::PortWidthMismatch { port,
declared, found }` on a mismatch. Every other `Module { .. }` struct literal
in the crate (7 in `ir/tests/validate.rs`'s hand-built fixtures, 1 in
`parse_line.rs`) needed the new field threaded through too.

New tests (+3, all `crates/mimz-core/src/ir/tests/validate.rs`):
`accepts_a_legitimately_sized_output_port` (a real `extend(a, 16)` widening,
no false positive), `rejects_an_extend_no_op_output_wider_than_its_declaration`
(the `extend(a << sh, 10)`-with-runtime-`sh` repro from gaps.md, built via
`lower()` on a real `Design` — worst-case `Shl` growth gives the base
expression 11 bits, `extend`'s no-op branch passes them straight through,
declared is 10 — caught), and
`hand_parsed_fixture_with_no_declared_width_skips_the_port_width_check` (a
hand-parsed `.ir` text module has an empty `port_declared_widths`, so the
check never fires, mirroring `accepts_a_blackbox_cell_with_no_declared_shape_on_record`).
Test count 1406 → 1409 in `docs/code/10-test-map.md` and the README badge
(lib-unit row 834 → 837).

## IR: `validate()` reports a pathologically-wide `Shl` instead of panicking (GAP-1 residual, task 3 of 6)

Closes the sharper half of GAP-1's "checker-legal program can panic"
residual: `ir::lower`'s own `bits[8] << 999000`-shaped panic is accepted
(no production caller), but `validate()`'s identical
`width_rules::shift_result(...).expect(...)` in its `Shl` cross-check
formula was a real bug — `validate()` exists specifically to REPORT
malformed IR, not crash on it, so a hand-written IR text fixture with an
oversized `Shl.b` pin panicked the validator instead of yielding a
`ValidationError`.

`expected_widths` (already `Result`-shaped groundwork from Tasks 1/2's
`module`/`driver` parameters) changed its return type from
`Vec<(&'static str, u32)>` to `Result<Vec<(&'static str, u32)>, (u32,
u32)>`. Every arm but `Shl` just wraps its existing literal in `Ok(...)`,
unchanged. The `Shl` arm now matches `width_rules::shift_result`'s own
`Ok`/`Err` (still calling the already-shipped `shl_const_amount(module,
driver, &pins["b"])` exactly as before) instead of `.expect()`-ing it,
returning `Err((a_w, b_w))` on overflow. The checks-2&3 loop in
`validate()` now matches this `Result`: `Ok(widths)` runs the existing
per-pin comparison unchanged; `Err((lhs_width, amount_width))` pushes a
new `ValidationError::ShiftGrowthTooWide { cell_index, lhs_width,
amount_width }`.

## IR: re-verified fused shift chains after Task 1 — already closed, no fusion needed (GAP-1 residual, task 4 of 6)

Task 1 fixed `Shl`'s per-cell sizing to be exact (not worst-case) for a
compile-time-constant shift amount, but the gaps.md "fused shift chains"
issue predates that fix and was never re-checked against it: does
`ir::lower` (which still lowers each `Shl`/`Shr` as its own independent
cell, with no chain-fusion pass) now agree numerically with the AST
kernel's `value::binary::eval_shift_chain` (which evaluates a whole chain
as one fixed-width unit) — as a side effect, since both fold the SAME
`width_rules::shift_result` formula at each step? This was a hypothesis
from reading the code, not a proven fact (BUG-34 itself was found by an
external fuzz oracle), so the task was to check empirically before doing
anything else — and, per the task brief, to STOP and flag for a scoping
decision rather than attempt a lowering-side fusion redesign inline if the
check turned up a real divergence.

Added a regression test lowering three shift-chain shapes through
`ir::lower` + `ir::exec` and comparing every result, bit-for-bit and
width-for-width, against `value::eval` driving `eval_shift_chain` directly
on the same expression, over the whole 256-value domain of an unsigned
8-bit input: BUG-34's exact repro (`(p2 >> 4) << 7`), its mirror (`(p2 <<
3) >> 1`), and a 3-step chain (`((p2 << 2) >> 3) << 4`). Zero divergences —
768 comparisons across the three shapes, both value and width agree in
every case. Confirms the hypothesis: an unsigned value's number doesn't
depend on how many extra zero bits sit above it in its container, and
Task 1 already makes every cell's local width formula exact-when-provable,
not just the outermost one — so a per-node-lowered chain and a fused one
carry the same container width at every step, not just the final one.

No lowering-side fusion logic was written — the brief is explicit that
adding it would be unrequested complexity for a problem the empirical
check shows no longer exists.

New test (+1, `crates/mimz-core/src/ir/tests/lower_binops.rs`):
`shift_chains_lowered_per_node_match_the_ast_kernels_fused_evaluation`.
Test count 1410 → 1411 in `docs/code/10-test-map.md` and the README badge
(lib-unit row 837 → 838). Left a pointer comment at `value::binary::
eval_shift_chain` (`crates/mimz-core/src/value/binary.rs:540`) naming this
test, so a future change to either side's width-folding rule has something

## IR: ordering comparisons carry a `signed` flag (GAP-1 residual Task 5)

`signed(a) < signed(b)` lowered to an UNSIGNED compare. `CellKind::Lt`/`Le`/
`Gt`/`Ge` were unit variants with nowhere to record signedness, and
`ir::exec`'s `get_bits` reconstructs every pin as `Val::new(acc, width,
false)` — so `signed(-1) < signed(1)` answered FALSE (`-1`'s bit pattern
being the largest unsigned 8-bit value), while `emit_verilog` renders the
same source as a genuinely signed `$signed(...)` comparison. The one GAP-1
residual that needed the IR to track SOME signedness.

Scoped to the four ordering `CellKind`s rather than threading a `Kind`-style
width+signed pair through `lower_expr`'s whole return type (the "real" fix
GAP-1 floats, and a much larger change than this residual needs).
`ir::Bits` is unchanged — still no sign bit anywhere in the netlist.

- **`ir/mod.rs`**: `CellKind::{Lt,Le,Gt,Ge}` gain `signed: bool`. Additive
  (a new field on existing variants, not new variants). `Eq`/`Ne` stay unit
  variants on purpose: two's-complement equality is sign-agnostic.
- **`ir/lower.rs`**: new `expr_is_definitely_signed`, the mirror of the
  existing `arg_is_definitely_unsigned` and shape-for-shape aligned with
  `emit_verilog::kinds::infer_kind`/`infer_binary` so the two back ends agree
  on when a comparison is signed. Computed at the one `ExprKind::Binary` call
  site (where the source `Expr`s still exist) and threaded into `lower_binop`
  alongside `shl_const_amount`, exactly like Task 1's parameter.
- **`ir/exec.rs`**: `binop_signed` re-tags BOTH operands' `Val.signed` before
  `binary_ctx`, so `value::binary::cmp_lt` takes its signed path. `binop` is
  now `binop_signed(.., false)`; `get_bits` itself is untouched, so every
  other cell kind's operands stay unsigned exactly as before.
- **`ir/print_line.rs` / `ir/parse_line.rs`**: unsigned keeps the bare `$lt`
  spelling (pre-existing IR text still means what it did), signed prints as
  `$lt[signed]` in the same bracket style as `$dff[Rise]`. Literal match arms
  rather than a `bracket_arg` branch — the two spellings are a closed set, so
  a typo'd `$lt[signd]` falls through to the unrecognized-op error instead of
  silently defaulting to unsigned. `print_sexpr.rs` needed no change at all:
  it reuses `print_line::cell_op_name` directly.
- **`ir/validate.rs`**: `requires_matched_ab`'s patterns became `{ .. }`.
  Confirmed by reading it that the a/b-width rule is orthogonal to
  signedness — no logic change.

**`Gt`/`Ge` got the field but no new lowering.** `BinOp::Gt`/`Ge` still fall
into `lower_binop`'s `unimplemented!()` catch-all, left byte-for-byte
unchanged — `ir::lower` has never produced a `Gt`/`Ge` cell. The variants
took the field for schema consistency because they ARE reachable from
hand-written IR text via `parse_line` and already dispatched by `exec`. So
they are schema-consistent and sign-aware when executed, but not
independently lowered; `Lt`/`Le` are the only ones with real new behaviour.

**One boundary deliberately not crossed.** `lower_binop` marks a comparison
signed only when its operands agree on WIDTH as well as sign. Two
non-literal operands always do — `checker::widths::ops::matched_ty` rejects
a mixed comparison outright (E0403), so this costs nothing there. A width
mismatch means the narrow side is a bare literal, which the checker types as
untyped `Ty::CtInt` inheriting the sized side's type — but `lower_expr`'s
`Int` arm sizes it at its own natural width (`5` → 3 bits), and reading
those 3 bits as two's complement would make `5` into `-3`, flipping `1 < 5`
from true to false. Caught empirically while writing the tests (the first
draft asserted the aspirational behaviour and failed). So `x < 5` for signed
`x` stays unsigned: still divergent from `emit_verilog`, but unchanged
rather than newly and differently wrong. Sizing a literal from its
comparison context is the separate follow-up that closes it.

New tests (+4): `signed_ordering_comparisons_execute_with_the_right_sign`
and `a_natural_width_literal_operand_keeps_the_comparison_unsigned` in
`crates/mimz-core/src/ir/tests/lower_binops.rs`;
`round_trips_signed_and_unsigned_ordering_comparisons` (all four operators,
both spellings — the only round-trip coverage `Gt`/`Ge` have) and
`an_unknown_comparison_bracket_argument_is_rejected` in
`crates/mimz-core/src/ir/tests/parse_line.rs`. Test count 1411 → 1415 in
`docs/code/10-test-map.md` and the README badge (lib-unit row 838 → 842).

`docs/audit/gaps.md`: marked the signed-comparison paragraph RESOLVED, being
explicit about the four scoping lines above — additive schema, `Eq`/`Ne`
untouched, arithmetic still unsigned, `Gt`/`Ge` schema-consistent but not
independently lowered — plus the narrowed literal-width residual.
