## BUG-15 fixed — bundle-field expansion for sim instance ports and `fn` call arguments

Branch `bug-15-bundle-field-expansion` (off `sim-runtime-diagnostics-r2`).
`mimz-sim` previously had no bundle-field-expansion baseline at two of the
four sites `mimz-core`'s emitter already covers: a bundle-typed
module-instantiation port connection, and a bundle-typed `fn` call
argument — both silently unsupported (BUG-15, filed during the `?`/`??`
valid-bundle-sugar feature's Task 10).

**Instance ports** (`crates/mimz-sim/src/sim/elaborate/instance.rs`):
`flatten_instance` rebuilds a `flat_field → (port, field)` map from the
child's own declared ports, since `elaborate_module` had already
flattened a bundle-typed port to per-field `Signal`s by the time
`child.inputs` reaches this function — the original `(port, field)`
pairing no longer existed anywhere. Each connection now expands per
field via the existing `bundle_field_expr` helper (already used by `??`
and Wire/Drive), rewritten through `Rw`. Root cause of why this never
worked: `prw` (the parent-context rewriter processing connection
expressions) was built with an always-empty `bundle_sigs` set — correct
reasoning for `crw` (the child body is already fully flattened) but wrong
for `prw`, since a connection expression lives in the PARENT's own
still-unflattened scope. Fixed by threading the parent's real
`bundle_sigs` through (a new `flatten_instance` parameter).

**`fn` call arguments**: two-sided fix, since both the call site and the
callee's own body reference the bundle value by its pre-flattening name.
(1) `Rw::expr`'s `FnCall` arm (`rewrite.rs`) gained `expand_fn_call_args`,
which expands a bundle-typed argument into one sub-expression per field —
keyed by the CALLEE's declared parameter type, not the argument's own
inferred type, mirroring the emitter's identical BUG-10 convention. This
needed `Rw` to carry `func_reg`/`bundle_reg`/`imports`, threaded through
all four `Rw` construction sites (`module.rs`'s `build_rw`, `instance.rs`'s
`prw`/`crw`, `rewrite.rs`'s own nested `ext_rw`). (2) A new
`flatten_bundle_params_in_func` (`bundle.rs`) pre-expands a `FuncDecl`'s
bundle-typed parameter into N flat scalar params and rewrites every
`param.field` body reference to the matching flat name — run ONCE when
`Elaboration::new` builds its `funcs` map, so `eval_fn_call`'s own runtime
param-binding loop needed zero bundle-awareness added: both the expanded
call-site args and the callee's own expanded params already agree on
field count/order/names by the time it runs. No `Resolver` trait changes
— the whole fix lives at elaboration time.

Two new regression tests in `crates/mimz-sim/src/sim/elaborate/tests.rs`
drive a real `kernel::Sim` end-to-end for each half. Full workspace
1115/1115 (1113 pre-fix baseline + 2 new), `cargo fmt --check` and

`docs/audit/bugs.md`'s BUG-15 entry updated to FIXED with the full

## BUG-26 and BUG-27 fixed — the last two sim-diagnostics catalog gaps

Branch `bug-26-27-diag-codes` (off `bug-15-bundle-field-expansion`). Both
were LOW-severity, correct-behavior-wrong-code gaps left open by R2's own
`sim_errors.rs` contract test.

**BUG-26**: `resolve_module`'s own "unknown module" `S0101` arm was dead
code — its only caller (`resolve_target`) always pre-checks
`reg.contains_key` first, so the arm could never fire. Deleted rather
than given an artificial live path: `resolve_module` now `.expect()`s the
invariant its caller already guarantees, and `S0101` is retired from
`ALL_SIM_CODES` (79 → 78) — the append-only contract never applied to a
code that could never fire.

**BUG-27**: `sim/comb.rs`'s `Env::resolve` builds a real, correctly-coded
`S0238` combinational-cycle `Diag`, but it always lost that code crossing
the `Resolver::signal` trait boundary (bridged to a plain `String` via
`.map_err(|e| e.msg)`, then re-coded as the generic `S0201` by
`eval_ctx`'s Ident-read). Fixed with a small marker-based smuggling
mechanism (`sim::diag::bridge_code`/`diag_from_bridged`) that preserves
the original code across the bridge without touching the `Resolver`
trait's own `Result<_, String>` signature — Phase 2's original "leave the
trait alone" constraint stays intact. Found and fixed the identical gap
in `sim/kernel.rs`'s `CombEnv::signal` along the way (the REAL simulator's
own cycle detection, not part of BUG-27's original filed scope but the
same condition): it built its cycle message as a bare, uncoded `String`
entirely, so it also always surfaced as `S0201` — now reuses `S0238` via
the same bridge.

Both fixes are elaboration/runtime-internal only — no CLI-visible
behavior change beyond the error CODE now matching the message (the
cycle was always correctly rejected either way). One test updated
(`s0238_combinational_cycle_fires_with_its_own_code`, now asserts the
code, moved out of `known_gaps`), one comment block removed. Full
workspace 1115/1115, `cargo fmt --check` and `cargo clippy --workspace
--all-targets -- -D warnings` both clean. `docs/audit/bugs.md` and
`docs/code/13-tooling.md`'s `S0xxx` catalog both updated.
