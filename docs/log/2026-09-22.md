## Fixed: GAP-1 closure Task 7 — `foreach`/`loop` unrolling in `ir::lower`

- Closed the last remaining `ir::lower` gap before the optimizer track:
  `FnStmt::Loop`/`FnStmt::ForEach` and `SeqStmt::Loop` all hit
  `unimplemented!()` on any `loop`/`foreach` construct inside a `fn` body or
  an `on`-block.
- `FnStmt::Loop` unrolls via plain statement splicing — for each value in
  the (checker-guaranteed const-foldable) range, splice a synthetic
  `FnStmt::Let(var = <literal>)` plus a clone of `body` ahead of `rest`, then
  recurse `lower_fn_stmts` unchanged. Reuses the existing `Let`/`If`/`Return`
  arms verbatim: `Return`'s arm already discards the remaining statements,
  which is exactly first-match-wins priority across unrolled iterations, so
  `fn_array_search.mimz`'s `find_index` (duplicate matches, lower index must
  win) needed no special-casing.
- `FnStmt::ForEach` desugars to a single `FnStmt::Loop` via the pre-existing
  `ast::lower_foreach_fn` (already used by `value/fn_eval.rs` for the same
  reason) and is spliced the same way — `lower_fn_stmts` gained a
  `fn_params: &[FnParam]` parameter so the Elements-form's array-length
  lookup has something to resolve against.
- `SeqStmt::Loop` (the `on`-block half of the same gap) is the one genuine
  design change: `SeqStmt` has no `Let`-equivalent, so the loop var is bound
  by threading a new `locals: Option<&HashMap<String, Bits>>` parameter
  through `lower_seq_stmts`/`lower_target_rhs`/`lower_bitselect_write` —
  reusing the SAME channel `fn`-body calls already used for `lower_expr`,
  not a new side-channel. This mattered structurally, not just stylistically:
  `expr_memo` (lower.rs's expression cache) is gated on `locals.is_none()`
  precisely because a re-walked body normally means the same value every
  time — a separate side-channel binding would have silently served
  iteration 0's cached answer on every later iteration.
- Found mid-implementation, fixed: `is_const_foldable` excludes any name
  present in `locals`, so the loop var's sibling-context resize never fired
  for a genuine binary-op use (`acc <- acc +% i`) — only for index positions.
  Without a fix this is a real hard panic (`ir::exec::arith`'s
  `debug_assert_eq!(a.width(), b.width())`) on checker-legal source, not a
  silent bug. Fixed by also folding the loop var into `self.local_consts`
  (scoped shadow/restore per iteration, mirrors `FnStmt::Let`'s existing
  pattern) — does not touch `expr_memo`'s gate, does not touch
  `lower_bitselect_write`'s separate (accepted, non-blocking) constant-index
  inefficiency.
- `SeqStmt::ForEach` turned out to already be dead code: `elaborate::module`'s
  `lower_foreach_in_seq` pre-pass eliminates every on-block `ForEach` before
  a `Process` exists, matching three other `unreachable!()` call sites
  already in the codebase (`elaborate/mod.rs`, `elaborate/rewrite.rs`,
  `sim/kernel.rs`). Split into its own `unreachable!()` arm with a regression
  test proving the pre-pass invariant holds, rather than leaving it folded
  into the same `unimplemented!()` as `Loop`.
- Both `FnStmt::Loop` and `SeqStmt::Loop` defensively cap at
  `crate::REPEAT_BUDGET` before unrolling — the checker does not enforce this
  bound for either shape (unlike `Repeat`/module-item `ForEach`), matching
  `value/fn_eval.rs`/`sim/kernel.rs`'s own S0227 guard.
- Five new tests in `crates/mimz-core/src/ir/tests/lower_loops.rs`:
  `fn_loop_range_form_first_match_wins`,
  `fn_foreach_elements_form_accumulates_array`,
  `seq_loop_unrolls_into_four_const_bindings`,
  `seq_loop_var_resizes_against_a_wider_sibling` (asserts both a structural
  width and a computed `ir::exec` value, not just "doesn't panic"), and
  `seq_foreach_syntax_lowers_via_preexisting_unroll_pass`.
- `cargo test --workspace` clean (907/907 `mimz-core` lib), `cargo clippy
--workspace --all-targets -- -D warnings` clean, `cargo fmt --all --check`
