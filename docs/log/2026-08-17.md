## Round 6 plan — Task 6, teach the fuzz generator `fn` bodies and module parameters

Continuation of [`2026-08-16.md`](2026-08-16.md)'s Tasks 1–5. Task 6
(`docs/plan/v0.2-class-closure-round6.local.md`) closes the reachability gap
review-2026-08-15.md's Part 6 named: 5000/5000 clean runs meant nothing for
BUG-62, because the generator's grammar could never reach a `fn` body or a
module parameter at all — depth and value bias are irrelevant to a shape that
was never emitted.

**What changed**, `tests/differential_fuzz.rs` only:

- `gen_special_leaves`'s `fn` leaf: the body used to be a bare parameter
  passthrough (`fn identW(x) { x }`), which can never make `infer_kind`
  return `None` inside a `fn`. Now builds a real body over the `fn`'s own
  single param via `gen_expr_collecting` (shallow depth, no `special` pool —
  a `fn` can't see outer ports/instances/mem), forced onto the declared
  return width. Shared by both the comb and clocked generators automatically.
- `gen_module` (comb): about a third of programs now declare a module
  `parameter` (`W: int = <default>`) and materialize `&extend(p, W)` or
  `nand(extend(p, W))` as an extra output, reusing the existing GAP-11(a)
  "extra materialized port" mechanism rather than adding new plumbing.
  Deliberately kept OUT of the general `special`/`gen_leaf` pool: nesting a
  symbolic-width `extend` any deeper (e.g. under `wrap_builtin`'s `Trunc`)
  hits a documented, still-open ceiling in Task 3's own fix and would make
  the generator legitimately produce a checker-clean program `mimz compile`
  correctly refuses — right compiler behavior, but this harness assumes
  compile always succeeds, so the shape is kept at the one covered position.

a differential, or a named checker rule/grammar restriction/lowering pass

## Round 6 plan — Task 11, retire the tautological `debug_assert!`

`hoist_if_needed`'s second assert (`ports.rs`, inside the branch where
`verilog_self_determined_kind(expr)` returns `None`) compares a fresh
`infer_kind(expr, decls, env)` call against the caller's own `mimz_kind` —
round-6 review Part 5.3 found it tautological as currently invoked: every
`hoist_if_needed` call site computes `mimz_kind` as `infer_kind(expr,
&decls, &self.env)` immediately before the call, same `decls`/`env` still
in scope, so the assert re-runs the identical pure function on the
identical arguments a second time. Cannot fail today.

Re-counted the call sites rather than trusting the audit's number (it said
twelve, written before this plan's Tasks 2–4 touched the surrounding code):
**eleven** today, matching Task 7's own `HOIST_CALL_SITES` count, each
checked by hand to confirm the same pattern.

Considered replacing it with Task 1's `hoist_unresolved` (the plan's other
option) and ruled it out: that assert fires unconditionally, correct only
when `infer_kind(expr)` itself returns `None` (GAP-16's concern). This
assert guards a DIFFERENT, legitimate `None` — `verilog_self_determined_
kind` saying "Verilog's own rendering already equals mimz's width here,"
true for `Ident`/`Bool`/every classifier arm built on that claim. Wiring
`hoist_unresolved` in would fire on all of those ordinary cases.

Kept as-is, rewrote the comment to say so plainly: tautological today,
deliberately retained as a refactor tripwire for a future caller that
threads a `Kind` from a different expression or a stale/cached one — and
contrasted against the FIRST assert (the bare-identifier branch, a few
lines up), which is real, since its two sides come from genuinely
