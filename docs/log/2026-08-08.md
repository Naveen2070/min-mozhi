# 2026-08-08

## BUG-41 + SEC-10 closed — self-determined hoist gate collapsed to one exhaustive match

Task 2 of `docs/plan/v0.2-correctness-remediation.local.md`. The gate
deciding whether `emit_verilog`'s hoist machinery runs at all
(`expr::kind_is_inferrable`) and the classifier it gated
(`kinds::infer_kind`) were two hand-synced matches over the same
`ExprKind`/`Builtin` enums — `self_determined.rs` had already been made
exhaustive (BUG-28/29), but the gate in front of it still ended in
`_ => false`, silently disabling the hoist for any expression containing a
`fn` call, an instance port, an `if`, a `match`, or a memory read. BUG-41
reopened BUG-28's exact defect through those shapes; the gate's own
`panic!`-on-unhandled-shape design was SEC-10's adjacent concern.

**Fix.** `kinds::infer_kind` now returns `Option<Kind>` directly —
`None` where the gate used to say `false` — so there is one function to
keep exhaustive, not two to keep in sync. Filled in the five previously
unclassified shapes: `FnCall` (the `fn`'s declared return type),
`Field` (an instance's output-port width), `Index` (a memory's element
width, or 1 bit for an ordinary bit-select), `IfExpr`/`Match` (either
branch/any arm — the checker guarantees they agree). All five resolve
through the same `decls: &HashMap<String, Kind>` map `infer_kind` already
took — `build_decls` (`module/ports.rs`) now also populates it with
instance-output-port kinds (keyed `{inst}_{port}`, matching `expr.rs`'s
own `Field` rendering), memory-element kinds (`mem_elem_decl_key`), and
`fn`-return kinds (`fn_ret_decl_key`), so `infer_kind`'s signature never
grew a second parameter. `hoist_if_needed` now takes the already-resolved
`Kind` from its caller instead of re-deriving (and potentially
re-failing to derive) it internally.

**Tests.** Five new Icarus differentials in
`tests/self_determined_regression.rs`, one per BUG-41 repro (fn-call
operand, instance-port operand, if-expr operand, memory-read operand,
`extend` through a `fn` call — the last reproduces BUG-28's original wrong
emission byte-for-byte through the new shape). Watched all five fail
against the pre-fix code before implementing.

## BUG-45 found and fixed — hoisted wires spliced in before the declarations they reference

Verifying BUG-41's fix (in an environment with Icarus Verilog 14.0,
vs. the audit's own 12.0 baseline) surfaced a second, unrelated,
pre-existing bug: hoisted `wire __mimz_sub_N`/`assign` pairs are spliced
into the module body right after the port list — before `wire`/`reg`/
`mem` declarations and before instances are emitted. Any hoist
referencing one of those forward-references a declaration that appears
later in the file, which Icarus 14.0 rejects ("declaration after use")
even though Verilog module items are order-independent by the language
spec — 12.0 evidently tolerated it. Confirmed pre-existing (not caused by
the BUG-41 work above) three ways: reproduced on a fully unmodified
checkout via `git stash`, hit an already-shipped example
(`examples/english/shift_register.mimz`) and an already-passing
regression test (`bug_23_wrap_under_sibling_add_inside_a_concat_matches_icarus`)
neither of which this session touched, and confirmed that manually
reordering the emitted Verilog (declarations before hoists) makes Icarus
accept it unchanged.

**Fix.** A second insertion point (`hoist_pos`) captured after
`emit_instances` runs, used for `self.hoisted_decls` specifically; the
`clog2`/user-`fn` injection stays at the original `fn_pos` (function
declarations aren't order-sensitive in Verilog — confirmed empirically,
nothing regressed). Full detail: `docs/audit/bugs.md` BUG-45.

Fixing this unmasked two independent, already-broken self-checking
testbenches that had simply never run to completion before in this
environment:

- `tests/icarus/sc_pid_controller_tb.v` — wrong hand-calculated expected
  `control` values at cycles 3–4; the comments assumed the PI controller's
  `integral` term stays constant across a held-input cycle, but it is
  (correctly) cumulative. Re-derived the true values from Icarus itself
  and corrected the comments and assertions.
- `tests/icarus/sc_vga_pattern_tb.v` — an off-by-one tick count
  (`repeat(655)` one short of the `h_cnt=656` the next check assumes).

Neither the PI controller nor the VGA pattern generator design was wrong;
only the hand-written testbenches' arithmetic was.

Also regenerated Verilog goldens (`MIMZ_UPDATE_GOLDENS=1`) and rebuilt
`crates/mimz-wasm/pkg` (`wasm-pack build crates/mimz-wasm --target web
--release`) — both were comparing against the old declaration order.

## BUG-46 found, filed, not fixed

`showcase/english/melody_player.mimz` emits `((dur) * TICK)[(32)-1:0]` — a

this session — real width-rules design work (a symbolically-sized hoisted
wire), not a small change, and out of Task 2's scope.

(`self_checking_showcase_testbenches_pass`, `melody_player`); `fmt`/
`clippy -D warnings` clean.

## BUG-46 fixed — module parameter is just `Ty::CtInt` under another name

Revisited the same session: the "real width-rules design work" this bug
was filed against turned out to be the wrong framing. A module `int`
parameter never needs a symbolic-width hoisted wire — it needs to _adapt
to its sibling operand's `Kind`_, exactly like a bare integer literal
already does (the checker's own `ident_ty` types both as `Ty::CtInt`).

**Fix.** Two new helpers in `kinds.rs`: `adapts_to_sibling` (true for a
bare literal OR an `Ident` absent from `decls` — by this file's own
module-body-only domain, the latter can only be a module parameter) and
`adapted_lossless_operands` (resolves such an operand to its sibling's own
`Kind`, mirroring the checker's `adapt_lossless` growth rule for the
`Add`/`Sub`/`Mul` family). The pre-existing `is_bare_int`-only check in the
`AddWrap`/`BitAnd` family's arm widens to the same `adapts_to_sibling`,
matching `matched_ty`'s no-growth rule. `dur * TICK` now resolves to a
64-bit `Kind`, which is enough for `Trunc`'s base-hoist to fire.

**Verified** directly against Icarus (`wire [63:0] __mimz_sub_1; assign
__mimz_sub_1 = ((dur) * TICK); ... dur_cnt <= __mimz_sub_1[(32)-1:0];`),
then via `self_checking_showcase_testbenches_pass` (now passing) and the
full workspace suite (`REQUIRE_IVERILOG=1 cargo test --workspace
--release --no-fail-fast`) — one other showcase (`tamil-pure`'s `isai`,
same `TICK`-multiply shape) picked up the same hoist. Goldens regenerated
(`MIMZ_UPDATE_GOLDENS=1`) and `crates/mimz-wasm/pkg` rebuilt to match the
new (cosmetic-only) hoisted wire. New unit test:
`lossless_mul_with_a_module_parameter_adapts_to_the_sized_operand`
(`kinds.rs`). `docs/audit/bugs.md` BUG-46 and `docs/audit/security.md`
SEC-10 (closed by the same underlying `infer_kind` work back in Task 2,
but never updated from OPEN until now) both updated to FIXED. `fmt`/
`clippy -D warnings` clean.

## Task 3 (BUG-42) closed — `min`/`max` recurses into its own operands

`self_determined.rs` classified `Min | Max => None` on the reasoning that
both operands are same-width by the checker's own rule, so no mismatch is
possible — true of mimz's widths, false of Verilog's SELF-DETERMINED
widths. `min(extend(p, 11), extend(p, 11))` (`p: signed[6]`) renders as
`(((p) < (p)) ? ((p)) : ((p)))` — each `(p)` self-determines to 6 bits,
not mimz's 11, so the whole ternary self-determines to 6 bits and Verilog
zero-extends that into an 11-bit destination instead of sign-extending
mimz's own correct 11-bit result (2039 vs. 55).

**Fix.** `Min | Max` now recurses into both operands and takes `max` of
their own self-determined widths, the same shape `SignedCast`/
`UnsignedCast` already used. Re-audited every other arm under the
corrected question this bug exists to teach — "is this argument's
_rendered_ width necessarily its mimz width?", not "is this operator's
_result_ width necessarily its mimz width?" — all four survive unchanged
(`Trunc`, the three reductions, the three recursing casts/`Encoding`).
Recorded the corrected question in the file's own module doc comment.

**Tests.** `bug_42_min_max_mismatched_operand_matches_icarus`
(`tests/self_determined_regression.rs`), the bug's own filed repro,
watched fail pre-fix (kernel 2039, Icarus 55). Full workspace green
(1212 tests, `REQUIRE_IVERILOG=1`); `fmt`/`clippy -D warnings` clean.

## Task 4 closed — position matrix's axes, not a bigger test count

Task 4 of the plan. The static matrix (`tests/self_determined_regression.rs`)
and the fuzzer's generator were both audited on three independent axes —
which `Builtin`/`BinOp`/`ExprKind` is classified, whether the shared gate
even lets the classifier run, and whether the operand under test is a bare
identifier or itself a mismatched sub-expression — and only the first was
ever really covered. Axis 2 is exactly BUG-41's gap; axis 3 is exactly
BUG-42's.

**(a) Deleted a duplicate exhaustiveness check.** `matrix_shape`/
`ALL_BUILTINS`/`every_builtin_is_classified_in_the_matrix` were a SECOND,
hand-maintained wildcard-free match over `Builtin`, existing purely to
assert "every builtin was classified somewhere" — but the real
classifiers (`infer_call` in `kinds.rs`, `verilog_self_determined_kind`'s
`Call` arm in `self_determined.rs`) are already wildcard-free themselves,
so the compiler already refuses a 14th unclassified variant without this
copy. It also couldn't have caught BUG-42: `Min`/`Max` were correctly
bucketed `MatrixShape::Binary` right up until the bug shipped — a shape
descriptor, not a check against `self_determined.rs`'s actual per-operand
behavior. Deleted; the individual `matrix_*_in_concat_matches_icarus`
Icarus-pinned tests are the real coverage and are untouched.

**(b) One property, checked on real data instead of imagined.**
`hoist_if_needed`'s bare-identifier early return (`module/ports.rs`) has
always assumed — in its own doc comment, never verified — that a bare
identifier's declared `Kind` trivially equals what the caller computed.
Added a `debug_assert!` that actually checks it against `decls`. Turns
every example, regression test, and fuzz run that touches a bare-
identifier self-determined operand into a free assertion against a future
`infer_kind`/`build_decls` drift — the exact defect class BUG-41/BUG-42
shipped as silent miscompiles instead of loud failures. Since this repo's
suite runs almost exclusively via `cargo test --release`, and
`debug_assert!` is a no-op there by default, added
`debug-assertions = true` to `[profile.release]` (`Cargo.toml`) — same
"defense in depth" precedent already set there for `overflow-checks`. Ran
the full workspace suite (1211 tests) with it active: zero assertion
failures, confirming the invariant already holds everywhere it's
currently checkable.

**(c) Turned out already done.** The plan assumed the fuzzer's builtin
arguments were always a bare port name. They aren't, and haven't been
since GAP-5 direction 2 landed 2026-08-03: `wrap_builtin`
(`tests/differential_fuzz.rs`) already wraps an arbitrary recursively-
generated fragment, which is exactly what found BUG-42 itself (fuzzer,
`MIMZ_DIFF_FUZZ_N=400`, seed 12648675, minimized by hand). The one real
gap — a fuzzer-generated `fn` call, instance port, or `if`/`match`
operand (BUG-41's own axis) — would need the fuzzer to invent auxiliary
`fn` declarations and sub-module instantiation from scratch, real new
infrastructure disproportionate to this task's `(S)` sizing; BUG-41's
shapes already have dedicated hand-written Icarus differentials from
Task 2, which is adequate coverage for a small, enumerable, closed set of
AST shapes.

`fmt`/`clippy -D warnings` clean throughout.

## BUG-44 closed — `trunc` of a `signed` value renders as an always-unsigned part-select

Task 6 of `docs/plan/v0.2-correctness-remediation.local.md`. The task was
scoped to _minimizing_ an unminimized fuzz divergence; it minimized to a
two-line module and a one-expression root cause, so it was fixed in the same
pass.

**It survived tasks 1–3.** Re-running `MIMZ_DIFF_FUZZ_CLOCKED_N=400`
reproduced seed 202427830 byte-for-byte — kernel `y=13806`, Icarus `y=13726`
— on Icarus **14.0** here versus the audit's 12.0. So BUG-42 was not the
cause (the seed contains `min(extend(3,3), extend(3,3))`, which is why it was
a candidate), and the divergence is not Icarus-version-sensitive.

**Minimized by arithmetic, not by bisection.** The plan prescribed splitting
the top-level operators into separate outputs (the method that minimized
BUG-42). Back-solving the delta was faster and landed on the answer directly:
`13726 / 2 = 6863`, so Icarus's subtraction produced 15055 where the kernel
produced 15095 — a difference of exactly 40, which is `3 * -4` against
`3 * +4`. Only one sub-term can produce that: `trunc(r0, 3)` where `r0` is
`signed[8] = -20` (`0b11101100`), whose low three bits `0b100` are `-4` to
mimz and `+4` to Verilog. Compiling the two-line module that predicts
confirmed it in the emission itself:

```verilog
assign y = (a[(3)-1:0]);   // a is `input wire signed [(8)-1:0]`
```

**Root cause.** `trunc(x, N)` **keeps** its operand's signedness, and three
independent authorities say so — the checker
(`checker/widths/ops/builtins.rs`: `Ty::Signed(_) => Ty::Signed(n)`), the
simulator (`sim/value/fn_eval.rs`: `Val::new(.., v.signed)`) and the emitter's
own classifier (`emit_verilog/kinds.rs`: `signed: base_signed`). The emitted
text does not: `trunc` renders as an explicit part-select (BUG-36's own fix),
and a part-select is unconditionally **unsigned** in Verilog-2005 (IEEE
1364-2005 section 5.1.7) even off a `signed` wire. The one artifact that
actually reaches Icarus disagreed with all three.

Two live consequences, not one. It mis-extends into a wider signed target
(zero- where mimz sign-extends), **and** — because Verilog makes an arithmetic
expression unsigned if any operand is unsigned — it demotes the whole
surrounding expression, discarding a sibling operand's own `$signed`. The
second is what the seed hit.

**Fix.** Wrap the rendered part-select in `$signed(...)` when the truncated
operand's `Kind` is signed (`emit_verilog/expr.rs`, `Builtin::Trunc`). An
unresolvable base `Kind` keeps the previous unsigned rendering — the same
accepted residue every other `infer_kind` call site there already has.
`ExprKind::Slice` deliberately needs no equivalent: `width_rules::slice_result`
types a slice `signed: false` (BUG-21), which is precisely Verilog's own rule.
Checked the other always-unsigned Verilog constructs the emitter produces —
bit-select (`Val::new(bit, 1, false)`, agrees) and the `min`/`max`/`abs`
ternaries (signed when both arms are, which they are) — `trunc` is the only
site where a mimz-signed value renders as an always-unsigned construct.

Also verified, rather than assumed, that `hoist_slice_base_if_needed`'s
hardcoded `signed: false` is **not** a second instance: in Verilog an RHS
expression's signedness is self-determined from its own operands, independent
of the assignment target, so an unsigned hoisted-wire declaration does not
change the bits assigned into it — and that wire's only consumer is the
part-select now explicitly re-signed. No change made there.

**Not a fuzz-only bug — it was miscompiling a shipped showcase.** Two goldens
moved, and one of the changes is a real behavioral repair:

```verilog
-    assign __mimz_sub_5 = (__mimz_sub_4[(16)-1:0] + (d_diff));
+    assign __mimz_sub_5 = ($signed(__mimz_sub_4[(16)-1:0]) + (d_diff));
```

In `showcase/english/pid_controller.mimz` (and its `tamil-pure` twin
`pid_kattu`) the unsigned part-select demoted the whole add, so the signed
derivative term `d_diff` zero-extended instead of sign-extending — a wrong sum
for any negative derivative. Its own self-checking testbench did not catch
this: `d` is 0 on every cycle it exercises, so the mis-extended addend is
never non-zero. That is a genuine coverage hole in `sc_pid_controller_tb`,
noted and deliberately not folded into this fix. Separately confirmed that the
earlier correction to that testbench's expected values (made while fixing
BUG-45) was about `prev_error` update ordering and unrelated — it was **not**
masking this bug.

**What this says about the class.** `Kind` carries `width` **and** `signed`.
BUG-41, BUG-42 and Task 3's re-audit of every classifier arm were all reasoned
on the width half. `Trunc` was explicitly re-confirmed as "no mismatch
possible" on the grounds that _"an explicit part-select is exactly N bits
regardless of the base"_ — true, and entirely silent about signedness. Task 4's
`debug_assert!` cannot catch it either: it compares a bare identifier's `decls`
entry against the caller's `mimz_kind`, never a **rendered construct's** kind
against the mimz kind it claims to represent, which is what Task 4(b)'s
property as written actually specifies. So the position matrix has a fourth
axis, and Task 4's landed assert is narrower than its own plan text. Both
recorded in the plan; implementing (b) as specified (comparing the full `Kind`)
is the remaining work on the class.

**Tests.** Both watched fail before implementing, in
`tests/self_determined_regression.rs`:

- `bug_44_trunc_of_a_signed_value_stays_signed_in_verilog` — the minimal
  mis-extension, `extend(trunc(a, 3), 6)` with `a = 236`: kernel 60, Icarus 4.
- `bug_44_trunc_of_a_signed_value_as_a_multiply_operand` — the demotion the
  seed took, `unsigned(signed(extend(3, 3)) * trunc(a, 3))`: kernel 52,
  Icarus 12.

Seed 202427830 now passes; both fuzzers green at `N=400` (103 s). Full
workspace green, `fmt`/`clippy -D warnings` clean. Seed 202427830 still needs
adding to the replayed corpus in task 5 (GAP-11), which is unaffected by this
fix and remains open.
