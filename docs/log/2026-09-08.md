## IR: size a bare literal/const or a compile-time-constant expression to its use-context width (GAP-1 residual Task 3)

Builds on Task 2 (uncommitted in the working tree at the time of writing —
`design.consts` resolution for a plain `Ident`). `ExprKind::Int`'s arm sized
every bare literal at its own natural width, with no notion of the width its
use-context actually requires — real, not hypothetical: the plan's
investigation dumped `traffic_light.mimz`'s lowered IR and found
`ir::validate::validate` reporting `WidthMismatch`/`PortWidthMismatch` on it
and on `debug_wrapper.mimz`/`sync_loop_search.mimz`.

**Preflight resolved three open questions before writing code:**

1. `crate::value::const_eval`'s signature (`fn(&Expr, &BTreeMap<String,
i128>) -> Result<i128, Box<Diag>>`) matches this file's existing `Slice`
   call exactly, confirmed by reading `value/mod.rs`. Decided NOT to route
   `ExprKind::Int` through it though — its own doc says it narrows to `i128`
   for a STRUCTURAL size, never a DATA value, and a resized operand IS the
   data value; `ExprKind::Int`'s own `value: &Bits` field is already the
   checker's arbitrary-width const-fold, so reusing it directly avoids both
   the doc-contract mismatch and a lossy round trip.
2. `requires_matched_ab`: duplicated (not extracted) as a sibling
   `fn(op: BinOp) -> bool` in `lower.rs`, matching `validate.rs`'s
   `CellKind`-keyed list exactly. `CellKind` doesn't retain which `BinOp`
   produced it, so unifying the two would need a translation layer neither
   file has, for an 11-arm boolean lookup — not a numeric formula worth
   sharing the way `Shl`'s growth (`width_rules::shift_result`) already is
   between the two files.
3. `resolve()`: now looks up the signal's declared width itself from
   `design.outputs`/`design.wires` (the only two lists `design.comb` ever
   drives) before lowering, instead of threading a width parameter through
   from `lower()`'s calling loops.

**A fourth thing found only by testing against the real examples, not
anticipated by the plan:** `sync_loop_search.mimz` is NOT "one more instance
of the traffic_light shape" as the plan assumed. `ast::sync_loop_lower.rs`
desugars a loop's done-check as a genuine `BinOp::Sub` AST node (`hi - 1`,
by design left unfolded so the desugaring stays free of a `checker`
dependency), and `lower_binop`'s ordinary lossless-Sub growth formula
(`in_width + 1`) sizes it 5 bits wide regardless of both operands being
literals — WIDER than the 3-bit counter it's compared against, the opposite
direction from the literal-too-narrow shape the plan described. Fixed by
generalizing `lower_expr_sized`'s constant recognition to a third case (any
expression `crate::value::const_eval` can fold, gated to `locals.is_none()`
since `const_eval` has no notion of `locals` and could otherwise resolve a
shadowed local name against an unrelated design-level const), and by
picking which `Binary` operand to re-lower using a new `is_const_foldable`
predicate instead of "whichever side is narrower" — the width-direction
assumption that made this case invisible to the plan's narrower fix.

### Decision: how to recognize the two accepted residuals in the generalized `const_eval` fallback

- **Context:** the generalized fallback (anything `const_eval` folds,
  beyond bare `Int`/`Ident`) reopens two risks the narrower Int/Ident-only
  version didn't have.
- **Decision:** accept both, documented at `lower_expr_sized`'s definition
  rather than worked around.
- **Why:** (1) `const_eval` narrows to `i128`, so a compile-time constant
  EXPRESSION (not a bare literal, which keeps its own arbitrary-width
  `bits::Bits`) that evaluates past `i128`'s range would be silently
  truncated — vanishingly unlikely for what this fallback exists to fold
  (loop-bound/enum-tag arithmetic), never observed in any real example. (2)
  gating on `locals.is_none()` avoids the local-name-shadowing risk
  entirely; every real call site today already passes `locals: None`, so
  this costs nothing in practice.
- **Impact:** `crates/mimz-core/src/ir/lower.rs` (`lower_expr_sized`'s doc
  comment), `docs/audit/gaps.md` (same caveat recorded in the sub-gap
  entry).

New tests (`crates/mimz-core/src/ir/tests/lower_binops.rs`):
`debug_wrapper_shaped_bare_literal_in_a_wire_driver_sizes_to_the_declared_output_width`,
`traffic_light_shaped_enum_match_arms_size_their_tags_to_the_scrutinees_width`,
and
`sync_loop_search_shaped_compile_time_subtraction_sizes_down_to_the_narrower_counter_width`

`PortWidthMismatch`/`WidthMismatch`. Also updated a pre-existing pinned

is now sized to `x`'s width instead of its own natural width, so the guard

## IR: lower plain-vector bit-select `v[i]` (GAP-1 residual Task 5)

`ExprKind::Index { base, index }` when `base` is NOT a memory
(`indexed_mem(base).is_none()`) fell to the same catch-all as Task 4 —
`fn_return_guard.mimz`/`std/uart_tx.mimz` (all flavors) hit this. Preflight
found the plan's own assumption wrong: the checker does **not** require a
plain-vector single-bit index to const-fold, unlike `Slice`'s `hi`/`lo`.
`checker/widths/expr/lvalue.rs:72-102` (`index_in_range`) only range-checks
a `Ty::CtInt` index (line 75); `Ty::Bit`/`Ty::Bits(_)`/`Ty::Unknown` — a
genuine runtime signal — passes through unchecked (line 86). So both `a[0]`
(constant) and `a[i]` (runtime) are checker-legal, and both paths were
implemented: a constant index is pure re-pointing (no cell, identical
strategy to `Slice`); a runtime index composes the EXISTING `BinOp::Shr`
lowering (`base >> index`, via `lower_binop`, no new width formula) and
takes net-index 0 of the shift's own output — `Shr`'s output width is
always `a.width()` regardless of the shift amount, so bit 0 of that
freshly-allocated `Bits` is always net-index 0, a compile-time-constant
slice despite `i` being runtime.

New tests: `lowers_constant_index_to_a_single_bit_repoint` (asserts the
exact `NetId`, and that no cell was allocated) and
`lowers_runtime_index_via_shr_and_a_zero_slice` (asserts exactly one `Shr`
cell of the right width, and the result pointing at its net-index 0).

`docs/audit/gaps.md`: new sub-gap entry, RESOLVED, inserted after Task 4's.

## IR: lower array-typed `fn` params, N-scalar flattening (GAP-1 residual Task 6)

`lower_expr`'s `ExprKind::FnCall` arm refused any `fn` whose parameter was
`Type::Array { .. }` outright — `fn_array_search.mimz`, `foreach_sum.mimz`,
`kootu.mimz` hit this. First dispatch came back BLOCKED, correctly: the
task's own brief scoped this to `call_locals` construction only, but the
`fn` body's OWN element access (`vals[i]`) had no path to reach flattened
locals — Task 5's `ExprKind::Index` arm treated every `base[index]` as a
plain-vector single-bit select, with no array-scope concept anywhere in
`ir::lower.rs` (confirmed by grep: zero `arrays`/`array_len`/`ArrayScope`
hits outside the investigation itself). Both `emit_verilog` and the
AST/value evaluator (what `mimz-sim` runs on) already have a proven,
identical convention for this — an array-typed param of length N flattens
to N scalar bindings `"{param}_{i}"` — but `ir::lower` had no equivalent on
either the binding side or the read side.

**Ruling:** fold `call_locals` construction and a new array-aware branch in
`ExprKind::Index` into one task (the two ends don't work independently),
overriding the brief's original file-scope line. Implemented: `arrays:
Option<&HashMap<String, u32>>` threaded alongside `locals` through
`lower_expr`/`lower_expr_sized`/`lower_fn_stmts`/`lower_match` (~40 call
sites, `None` only at the module-level entry points that are never inside a
`fn` body); `FnCall`'s `call_locals`/`call_arrays` rewritten to bind each
array-typed argument's elements individually (relying on the checker's own
E0413 array-length/element-width enforcement rather than re-deriving it);
`ExprKind::Index` gained a new branch, checked before the existing
plain-vector logic, that recognizes a bare `Ident` naming an in-scope array
— a constant index resolves directly to `locals["{name}_{i}"]` (no cell),
a runtime index folds an `Eq`/`Mux` chain from the last element backward
(mirroring `lower_match`'s own reverse-fold pattern, composing only
already-existing cell kinds).

New file `crates/mimz-core/src/ir/tests/lower_array_fn_params.rs`: a
constant-index test (asserts the picked element's `Bits` equals the
argument's own port `Bits` exactly, zero cells) and a runtime-index test
(walks the full `Eq`/`Mux` chain by concrete pin identity, decoding each
`Const` cell's index value, confirming the clamp-to-last-element default).

`docs/audit/gaps.md`: one combined sub-gap entry (not two), explicitly
narrating the scope expansion. Also fixed a real, pre-existing
`docs_sync.rs` failure surfaced by `cargo test --workspace`: Tasks 4/5/6

## IR: mark `BinOp::Coalesce` unreachable in `lower_binop` (GAP-1 residual Task 8)

Corrects an earlier sub-gap entry's own history: a first pass at explaining
why `BinOp::Coalesce` was the one variant `lower_binop` still handled via the

**Preflight re-confirmed both citations directly** rather than reusing them:

**Empirical verification, not just re-reading source:** added
