- Every resulting file is under the 1,000-line threshold.

**The two non-mechanical steps** (unlike A/B/C, which were pure file
motion): `binary_known`'s single 11-arm match decomposed into one named
function per `BinOp` (add/sub/mul/±wrap/bitand/bitor/bitxor/shl/shr, the
comparison/logic ops left inline as one-liners); `elaborate_module`
decomposed into an `Elaboration<'a>` struct owning both its read-only
per-module context and its 11 mutable worklist accumulators (`inputs`/
`wires`/`regs`/`comb`/`procs`/... - too much shared mutable state for a
plain per-`ModuleItem`-variant function split to read cleanly), split
into `new`/`rw0`/`width_of`/`lower_items`/`run_worklist`/`finish`. Both
decompositions copied every line of logic verbatim (arm/step bodies
unchanged, only the enclosing `fn`/`impl` wrapper and, for
`elaborate_module`, the bare-local → `self.field` rewrite are new) and
were verified by a dedicated deep differential-fuzz pass
(`MIMZ_DIFF_FUZZ_N=500` + `MIMZ_DIFF_FUZZ_CLOCKED_N=2000`,
`REQUIRE_IVERILOG=1`) before their file cut - the `elaborate_module`
decomposition specifically hit one borrow-checker complication the
design spec's pseudocode didn't spell out: a `&self`-taking `rw0()`
method can't be held live alongside a simultaneous `&mut self.comb`/
`&mut self.bit_drives` in the same statement (the 3 `record_drive` call
sites), fixed via a `build_rw()` free function that takes individual
field borrows instead, keeping the borrow checker's disjoint-field
visibility intact.
