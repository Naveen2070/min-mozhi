## Verdict

Round 6's remediation is, bug for bug, real — and this is the first round where
the fixes hold up under exhaustive rather than spot verification. All **ten** of
BUG-62's reproductions agree with Icarus. BUG-63 is clean across **all 4096**

invisible. BUG-64/65: I swept the whole shipped corpus myself — **50 files, 90
emitted testbench modules, 0 failures**. Both fuzzer acceptance criteria
reproduce from scratch at 400/400 on the seeds the plan records. Deep fuzz at
**5000/5000, debug: 5/5 passed, 1136.38 s, CLEAN**. Repo green, fmt/clippy clean.

**And the class is still open, for the seventh round running.**

The round's assigned question, answered plainly:

> **A fourth context exists. So do a fifth and a sixth. Task 1's invariant
> caught two of the four on its own, without being asked — the first time in
> this series that an instrument found a defect a reviewer had not already
> found. It could not have caught the other two, because they are not on the
> axis it watches.**

The four are two distinct families:

**Family A — the hoist buffer is flushed _after_ three render sites that can
hoist.** `module()` captures `hoist_pos` at `module/mod.rs:385`, but renders
expressions at three earlier points. Anything hoisted from those is declared
after its own use:

```text
let u = Sub() { d: { b, extend(a, 8) } }
  emitted   Sub u (.d({b, __mimz_sub_1}), .q(u_q));
            wire [7:0] __mimz_sub_1;                 ← declared AFTER
  iverilog  error: Unable to bind wire/reg/memory `__mimz_sub_1' in `tb.dut'
```

— from an **instance port connection** (`emit_instances`, pre-existing and
unfound for six rounds), from a **`reg` reset `initial` seed** (which is
**round 6's own BUG-65 fix**, one commit old), and from a **`mem` init loop**
(pre-existing). All three: `mimz check` OK, `mimz compile` **exit 0**, Icarus
refuses. **Task 1's invariant cannot see any of them** — `infer_kind` resolves,
the hoist fires correctly, only the placement is wrong. This is a `Some(k)`
path; the invariant watches `None`.

**Family B — a `decls` map built from an incomplete source.**

```text
fn inner(x: bits[4]) -> bits[4] { x }
fn outer(x: bits[4], c: bits[4]) -> bits[12] { { c, extend(inner(x), 8) } }
  mimz compile   thread 'main' panicked at ports.rs:784:9: hoist_unresolved …
  (assert off)   outer = {c, (inner(x))};   mimz 2575   iverilog 175
```

That is **BUG-28 again**, byte for byte, in a **sixth** context — a `fn` calling
another `fn`. Cause: `render_fn_decl`'s fresh `fn_decls` (Task 2) omits the
`__mimz_fnret__` keys `build_decls` inserts at `ports.rs:222-226`. And
`emit_testbench` builds its decls from **unflattened** `dut.items` while
`module()` uses `flatten_items` — so every port a `const if`/`sync loop`/
`foreach` generates is invisible to the testbench, both to the hoist machinery
and to the testbench's own port-declaration loop:

```text
const BIG: int = 1
module Fuzz { in a: bits[4]  const if (BIG == 1) { out y: bits[4] }  y = a }
test "t" for Fuzz { a = 0b1111  expect y == 0b1111 }
  mimz test        1 passed, 0 failed
  emitted tb       no `wire y`, no `.y(y)` connection
  iverilog         error: Unable to bind wire/reg/memory `y' in `constif_plain_tb'
```

**Task 1's invariant caught both of Family B** — the nested-`fn` case and the
hoisting half of the testbench case both surface as its assert, on shapes
nobody in this series had written down. That is a real result, and it is the
first genuinely forward-looking artifact the project has produced. Two caveats
that matter: the loud form is a **panic, not a `Diag`** (`requires_named_wire`
is false for a concat member), and `[profile.release] debug-assertions = true`
means shipped release binaries **abort** on those two checker-clean programs;
and the port-declaration half of the testbench bug is invisible to it.

Separately, three findings the brief asked for by name:

- **The two "honest open gaps" (if-expr then/else branch) are SAFE — and I
  built the differentials that prove it.** `y = extend((if c { a +% a } else
{ a }), 8)` with `a = 0b1111`: HEAD gives 14 both sides; with `expr.rs:414`/
  `416`'s hoists removed, mimz 14 vs Icarus **30** (and 1 vs **225** for `*%`).
  Both sites are load-bearing. Removing them fails **only** the exhaustiveness
  guard's count check — **no behavioural test in the suite notices**.
- **BUG-65 is a real, unrecorded scope increase on F-5/BUG-32.** Strip the four
  `initial <reg> = …;` lines from `std/fifo.mimz`'s emitted Verilog (an ASIC
  power-up model) and **all three of its shipped tests flip from PASS to FAIL**.
  50 shipped testbenches now depend on an FPGA/simulation-only construct.
  The emitted per-module NOTE says so; BUG-32, `gaps.md`, and
  `docs/guide/04-signals.md`'s ASIC caveat (still scoped to `mem` only) do not.
- **`wasm_parity` is not a flake — it is a dead test.** `run_parity` returns
  early when `crates/mimz-wasm/pkg` is absent. That directory does not exist
  here, and **CI never builds it** (no `wasm` anywhere in `ci.yml`). Both tests
  are vacuous passes, locally and in CI, contributing 2 of the 1270. Round 6's
  diagnosis ("a pre-existing native/WASM emitter parity gap") is wrong in kind:
  `mimz-wasm` compiles the same `mimz-core` emitter, so a rebuilt `pkg` cannot
  diverge. What Task 6 saw was a **stale build artifact** predating BUG-65's
  new emitted NOTE line.

## Part 3 — The round's primary question: a fourth context

I audited every place the emitter renders an expression. There are exactly three
emitter _contexts_ (`module()`, `render_fn_decl`, `emit_testbench`) — there is no
`--emit-netlist` or debug-dump path; `compile -d` prints timing only. But
"context" turned out to be the wrong unit. The defects this round are at
**render sites within** those contexts.

### 3.1 BUG-66 (HIGH) — a hoisted wire is declared after three render sites

**Status: OPEN at `7286b71`.**

`module()` captures the hoisted-declaration insertion point once:

```rust
self.emit_instances(&m.items);          // module/mod.rs:371
let hoist_pos = self.out.len();         // module/mod.rs:385
```

Three render sites run **before** that line and can each push into
`self.hoisted_decls`:

| #   | site                                                                                  | source (`module/mod.rs`) | age                                   |
| --- | ------------------------------------------------------------------------------------- | ------------------------ | ------------------------------------- |
| A1  | instance input port connections (`self.expr(&conn.signal)`, `instances.rs:237`/`246`) | line 371                 | pre-existing, six rounds              |
| A2  | `reg` reset `initial` seeds (`self.expr(reset)`)                                      | line 361                 | **new in round 6 — BUG-65's own fix** |
| A3  | `mem` init/depth (`self.expr(init)`/`self.expr(depth)`)                               | lines 322-323            | pre-existing                          |

Three reproductions, all `mimz check` **OK**, all `mimz compile` **exit 0**:

| #   | source                                     | emitted                                                             | Icarus                                   |
| --- | ------------------------------------------ | ------------------------------------------------------------------- | ---------------------------------------- |
| A1  | `let u = Sub() { d: { b, extend(a, 8) } }` | `Sub u (.d({b, __mimz_sub_1}), …);` then `wire [7:0] __mimz_sub_1;` | `Unable to bind … declaration after use` |
| A2  | `reg r: bits[12] = { b, extend(a, 8) }`    | `initial r = {b, __mimz_sub_1};` then `wire [7:0] __mimz_sub_1;`    | same                                     |
| A3  | `mem m: bits[12][4] = { b, extend(a, 8) }` | `initial for (…) m[i] = {b, __mimz_sub_1};` then the wire           | same                                     |

A1 also reproduces through a `repeat`-unrolled instance array (two wires, both
out of order). A machine check over the emitted `.v` of the whole shipped
corpus (226 files) finds **zero** out-of-order references — which is exactly why
the goldens and the Icarus suite are green, and exactly the pattern round 6
described: every instrument in the project watches the module-body expression
emitter.

**Task 1's invariant would not have caught this, and cannot.** `infer_kind`
resolves fine here (the module's own `decls` are installed), the hoist fires,
and the wire is correct. Only its _position in the output_ is wrong. The
invariant is defined over the `None` branch; this is the `Some(k)` branch. This
is a **second scoping axis** — not "which `decls` is in scope" (round 6) but
"when is the hoist buffer flushed relative to this render" — and nothing in the
project watches it. Filed as [GAP-18](gaps.md).

**Severity HIGH**, not CRITICAL, for BUG-63's reason: Icarus refuses it loudly
today. It is a portability failure (tools that tolerate declaration-after-use
for nets would accept it silently and correctly), not a wrong-value bug.

**Fix shape.** Move `hoist_pos` above the `mem`/`reg`/instance loops — it cannot
go to `fn_pos` (BUG-44's own note explains why: a hoisted wire may reference a
`reg`/`wire`/`mem` or an instance output). The lazy correct form is a second
buffer, or capturing `hoist_pos` after the declaration loops but rendering the
three sites' expressions into a deferred buffer spliced after it.

### 3.2 BUG-67 (HIGH) — a nested `fn` call: BUG-28, sixth context

**Status: OPEN at `7286b71`.**

`build_decls` inserts one reserved key per project `fn` for its declared return
`Kind` (`ports.rs:222-226`), and `infer_kind`'s `FnCall` arm reads exactly that
key (`kinds.rs:213`). Task 2's `render_fn_decl` builds a **fresh** map from the
`fn`'s own params and `let`s (`funcs.rs:92-117`) and never adds those keys. So a
`fn` calling another `fn` in a self-determined position is unresolvable:

```mimz
fn inner(x: bits[4]) -> bits[4] { x }
fn outer(x: bits[4], c: bits[4]) -> bits[12] { { c, extend(inner(x), 8) } }
module Top { in a: bits[4]  in b: bits[4]  out y: bits[12]  y = outer(a, b) }
```

```console
$ mimz check f3.mimz                        # OK
$ mimz compile f3.mimz -o f3.v
thread 'main' panicked at crates\mimz-core\src\emit_verilog\module\ports.rs:784:9:
hoist_unresolved: `infer_kind` returned None for Expr { kind: Call { func: Extend,
args: [ … FnCall { name: "inner" … } … ] } } at `concat member`
(rendered as `(inner(x))`) — GAP-16/BUG-62: a hoist site may not silently do
nothing when it cannot resolve a Kind.
```

The module-scope control is correct, which isolates the cause exactly:

```text
y = { b, extend(inner(a), 8) }      →  wire [7:0] __mimz_sub_1 = (inner(a));  ✅
```

Rebuilt with `-C debug-assertions=off` to see what the assert is standing in
front of:

```text
outer = {c, (inner(x))};
  mimz eval  y = 2575          iverilog  y = 175        ✗
```

**BUG-28's founding divergence, byte for byte, in a sixth context.**

Two things about the loud form. First, `[profile.release] debug-assertions = true`
(`Cargo.toml:104-119`, deliberate and documented) means a **shipped release
binary aborts with a Rust panic** on this three-line, checker-clean program —
`mimz compile` neither succeeds nor reports a diagnostic. Second, the site is a
concat member, so `requires_named_wire` is `false` and no `Diag` is pushed; the
panic is the only signal. A compiler crash is strictly better than a silent
2575-vs-175, and strictly worse than an error message.

**Fix shape.** One loop, copied from `build_decls`: add the `fn_ret_decl_key`
entries to `fn_decls` in `render_fn_decl`. `mem_elem_decl_key` and the
instance-port keys are correctly absent (a `fn` can read neither).

### 3.3 BUG-68 (HIGH) — `emit_testbench` reads an unflattened item list

**Status: OPEN at `7286b71`.**

`module()` works from `self.flatten_items(&m.items)`, which expands `const if`,
lowers `sync loop` and `foreach`, and runs `expand_sync_prims`
(`instances.rs:8-39`) — all of which can **declare ports, wires and regs**.
`emit_testbench` uses `&dut.items` **unflattened**, in two places: the `decls`
install Task 2 added (`testbench.rs:291`) and the testbench's own
port-declaration/connection loop (`testbench.rs:295`).

Two symptoms from one cause. The hoisting half:

```mimz
const BIG: int = 1
module Fuzz { in a: bits[4]  const if (BIG == 1) { out y: bits[4] }  y = a }
test "t" for Fuzz { a = 0b1111  expect &extend(y, 8) == 0 }
```

```console
$ mimz check ci2.mimz                       # OK
$ mimz test  ci2.mimz                       # 1 passed, 0 failed
$ mimz compile ci2.mimz --emit-testbench
thread 'main' panicked … hoist_unresolved … at `Unary reduction operand`
(rendered as `(y)`)
```

and with assertions off, `(&(y))` — **BUG-62 ⑨'s exact rendering**, in the
context Task 2 was written to close.

The port-declaration half needs no hoist at all:

```mimz
test "t" for Fuzz { a = 0b1111  expect y == 0b1111 }
```

```verilog
module constif_plain_tb;
  reg [4-1:0] a;
  Fuzz _dut_inst ( .a(a) );          // no `wire y`, no `.y(y)`
  …
  if (((y == 'b1111)) !== 1'b1) begin
```

```console
$ mimz test ci3.mimz            1 passed, 0 failed
$ iverilog -g2005 ci3.v ci3_tb.v
ci3_tb.v:18: error: Unable to bind wire/reg/memory `y' in `constif_plain_tb'
```

`mimz compile --emit-testbench` exits 0 having written a testbench that cannot
elaborate, for any DUT with a `const if`- or `sync loop`-generated port.
**Task 1's invariant caught the first half and is blind to the second** — a
missing port declaration is not a hoist question.

**Fix shape.** One word: `em.build_decls(&em.flatten_items(&dut.items))`, and
the same for the port loop.

## Part 5 — The two honest open gaps, resolved

Task 7 left `if-expr then-branch` (`expr.rs:414`) and `if-expr else-branch`
(`expr.rs:416`) marked as **genuine, open coverage gaps, not claimed proofs** —
no differential forces a plain (non-fused) width-effect/shift operator into a

## Part 12 — The structural finding

**1. Task 1 is the first thing in seven rounds that worked the way it was
supposed to.** It was written to make the _next_ unscoped context loud instead of
silent. There was a next context — there were two — and it was loud for both,
before any reviewer had a hypothesis. Every prior round's closure condition was
a rule about how to _review_ code; this one is a runtime check on the code
itself, and it is the only one that has ever paid out. That deserves saying
plainly, because the rest of this review is about what it does not cover.

**2. And the failure mode migrated again, one level sideways.** Round 6's
migration was from "which arm answers wrong" to "which `decls` map is in scope".
Round 7's is from "which `decls` map is in scope" to "**when is the hoist buffer
flushed relative to this render**". Same machinery, orthogonal axis, zero
instruments. Three render sites in `module()` sit above `hoist_pos`, and one of
them was added by round 6's own fix. Filed as GAP-18.

**3. The two axes have different shapes, and that matters for what to build
next.** The `decls` axis is a _data_ question — a map is missing an entry — and
an assert on `None` covers it generically. The flush axis is a _control-flow_
question — a buffer is emptied at the wrong point — and no `None`/`Some` check
can see it. What covers it is cheap and mechanical: **a post-emission check that
no `__mimz_sub_N`/`__mimz_fn_sub_N` is referenced before its declaration.** I
wrote that check in twenty lines of Python to find BUG-66, and it runs over the
226-file corpus in seconds. As a `debug_assert!` in `emit()` it would have caught
A1 six rounds ago, A2 the day BUG-65 landed, and it will catch the seventh
context for free.

**4. The instruments are now good enough that the remaining bugs are one-liners.**
This is new. BUG-67 is a missing loop of four lines. BUG-68 is one word
(`flatten_items`). BUG-66 is moving one `let`. The two "open gaps" turned out to
be safe. Compare round 6, where the fix list was three contexts and an
architecture. The gap to shippable really has narrowed this time, and it has
narrowed for a structural reason rather than by luck.

**5. What a green suite still doesn't mean.** Two of the 1270 are vacuous
(`wasm_parity`, dead in CI). Deleting two load-bearing hoists fails only a count
check. `demo/cpu.mimz`'s testbench is outside the new corpus sweep. The hoist
exhaustiveness guard scans one file. Every one of those is a one-line fix, and
together they are the difference between "green" and "green means something."

**6. The count.** Round 6 counted thirty in the "two implementations of one width
rule disagreed" family. Add BUG-66 (three sites), BUG-67 and BUG-68: **thirty-four**.
BUG-67 is BUG-28 again — the fourth time the founding bug has resurfaced in a
context nobody had looked at. GAP-1's argument is unchanged and, for the third
round running, sharper: a typed elaborated IR carries a width per node in every
context, and it also removes the buffer, because a hoisted node is just a node.

## Ship / do-not-ship

**Do not ship v0.2.**

Seven rounds, seven rounds of new instances. This one is the narrowest, and the
first where the closure mechanism did part of the work itself.

The round's assigned question, answered plainly: **a fourth context exists —
four do — and Task 1's invariant caught two of them on its own, before I had a
hypothesis, on shapes nobody in six rounds had written down.** That is a genuine
result and it should be recorded as one: it is the only fix in this series that
has survived contact with a context nobody thought of. The other two it could
not have caught, because they are not `None`-branch defects at all — they are on
a second axis of the same machinery, where the hoist buffer gets flushed, and
nothing watches that axis.

Categorised against the failure modes rounds 4–6 established:

| instance   | category                                                                                                                                                                                |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **BUG-66** | **a new axis entirely** — not "which `decls` is in scope" but "when is the hoist buffer flushed"; compounded by **a fix that created a sibling instance** (BUG-65 added render site A2) |
| **BUG-67** | **data source under-populated** — BUG-53's category, in a map created by round 6's own fix, missing a key its sibling constructor documents as required                                 |
| **BUG-68** | **data source under-populated**, twice from one cause — plus **position not analysed at all** for the testbench's own port-declaration loop                                             |
| **BUG-69** | **a fix that widened an existing, filed gap without saying so**                                                                                                                         |

Does Task 1's invariant need revision, or was BUG-66 a case it was never meant
to catch? **The latter, and that is the finding.** The invariant is correctly
scoped and correctly implemented for the axis it names. What is missing is its
counterpart on the second axis, and that counterpart is smaller than the
invariant itself: one `debug_assert!` over the emitted text, asserting no
hoisted name is referenced before it is declared. Every round since round 3 has
ended with "the gap to shippable is three XS fixes and one S," and every round a
further instance has been found in the remainder. The difference this time is
that four of the five items above are genuinely one-liners, and the fifth is a
twenty-line check that closes a whole category rather than an instance.
