Zero occurrences of `panicked` in the output. Exit 1. **No partial `ci2r.v` left

**`requires_named_wire: true`** (slice base), same binary:

The `cfg!(test)` gate is the right mechanism and the comment explaining it is
accurate: `debug_assert!` cannot distinguish "a developer's test hit this" from
"a user's release binary hit this" in a workspace that ships with
`debug-assertions = true`, and `cfg!(test)` can.

**One quality nit, not a blocker.** The user-facing `Diag` embeds a raw Rust
`Expr { kind: Call { func: Extend, args: [Expr { kind: Ident("y"), span: Span {
start: 156, … } } … ] } }` Debug dump. That is an internal-limitation message
leaking the AST into a shipped compiler's error output. Fine for a
`debug_assert!` panic; wrong for a `Diag` a user reads. Suggest keeping the
Debug dump behind an env var or dropping it from the `Diag` and leaving it in
the assert text.

### Item 5 — BUG-68, `flatten_items` in `emit_testbench` · **PARTIAL — the filed repro still fails**

The `flat_dut_items` change is real and correct as far as it goes (and went

Round 7's repro (b), verbatim, at HEAD:

```mimz
const BIG: int = 1
module Fuzz { in a: bits[4]  const if (BIG == 1) { out y: bits[4] }  y = a }
test "t" for Fuzz { a = 0b1111  expect y == 0b1111 }
```

```console
$ mimz check ci3.mimz                      # OK
$ mimz test  ci3.mimz                      # 1 passed, 0 failed
$ mimz compile ci3.mimz -o ci3.v --emit-testbench
compiled ci3.mimz -> ci3.v
compiled ci3.mimz -> ci3_tb.v (testbench)  # exit 0
$ iverilog -g2005 -o ci3.out ci3.v ci3_tb.v
ci3_tb.v:18: error: Unable to bind wire/reg/memory `y' in `t_tb'
ci3_tb.v:18: error: Unable to elaborate condition expression.
2 error(s) during elaboration.
```

Byte-for-byte round 7's Part 3.3 symptom. The emitted testbench has no
`wire y`, no `.y(y)`. Repro (a) likewise still fails, now as a `Diag` rather
than a panic (which is item 2 working correctly on top of an unfixed item 5).

**Root cause, and why the fix missed.** `flatten_items` evaluates the `const if`
condition against `self.env` (`module/instances.rs`) with `.unwrap_or(0)` on
failure. `emit()` sets `em.env = file_consts` before emitting modules
(`emit_verilog/mod.rs`). `emit_testbench` sets `em.env = test_env.clone()`
(`testbench.rs`) — **test args and module parameters only, never the file's own
consts**. So `BIG` is unresolvable there, `eval` errors, `unwrap_or(0)` silently
reads it as false, and the `const if` takes the _else_ branch — empty. The port
is dropped.

Control, isolating it to the env and not to `flatten_items`:

```console
$ # identical source, `const if (1 == 1)` instead of `const if (BIG == 1)`
$ iverilog -g2005 -o ci4.out ci4.v ci4_tb.v && vvp ci4.out
PASS
```

A literal condition works; a file-const condition does not.

**This was known and deliberately not fixed.** `tests/self_determined_regression.rs`
says so in its own words — the shipped regression tests use `const if (1 == 1)`
because the review's own repro "hits a separate, pre-existing gap this task
doesn't touch," and `bugs/bug-61-70.md` repeats it, ending "Not filed as its own
bug entry." That is an honest note in the wrong place: **BUG-68 is marked
`FIXED` while the reproduction printed under its own heading still fails**, and
the residue is neither filed nor on the RC's known-issues list. Filed below as
**BUG-71**.

### 2.2 It does not close the axis — BUG-70

The axis, as GAP-18 itself states it, is _"a buffer is emptied at the wrong
point → a correct wire lands after its use."_ The invariant implements something
narrower: _no `__mimz_sub_N`/`__mimz_fn_sub_N` is referenced before its own
declaration._ The gap between those two statements is every case where the
out-of-order symbol is **not** a hoisted name.

Item 3's own fix creates exactly such a case. `pre_decl_hoist_pos` is captured
_before_ `emit_instances`, but `emit_instances` emits each instance's output
wire declaration inline, interleaved with the next instance's connection
rendering (`module/instances.rs`). So a hoist raised by instance _N_'s port
connection is spliced ahead of instances _1..N-1_'s output wires.

**Construction 1** — not one of BUG-66's three repros:

```mimz
module Sub { in d: bits[12]  out q: bits[4]  q = d[3:0] }
module Top {
  in a: bits[4]
  in b: bits[4]
  out y: bits[4]
  let u1 = Sub() { d: { b, extend(a, 8) } }
  let u2 = Sub() { d: { b, extend(u1.q, 8) } }
  y = u2.q
}
```

```console
$ mimz check nc1.mimz
OK: nc1.mimz — 2 module(s), 0 test(s), 1 file(s)
$ mimz compile nc1.mimz -o nc1.v
compiled nc1.mimz -> nc1.v            # exit 0, invariant silent
```

```verilog
    wire [7:0] __mimz_sub_2;
    assign __mimz_sub_2 = (u1_q);      // <- use
    wire [(4)-1:0] u1_q;               // <- declaration
    Sub u1 (.d({b, __mimz_sub_1}), .q(u1_q));
```

```console
$ iverilog -g2005 -o nc1.out nc1.v
nc1.v:18: error: Unable to bind wire/reg/memory `u1_q' in `Top'
nc1.v:19:      : A symbol with that name was declared here. Check for
                 declaration after use.
2 error(s) during elaboration.
```

**Construction 2** — same axis through a different one of the three sites, to
confirm it is a property of the splice point and not of instances specifically:

```mimz
let u1 = Sub() { d: { b, extend(a, 8) } }
mem m: bits[12][4] = { b, extend(u1.q, 8) }
```

```console

nc2.v:23:      : … Check for declaration after use.
```

### 2.3 What this means for the claim

Three things follow, and they should be stated separately because they have
different weights.

**(a) The invariant is name-specific, not axis-level.** GAP-18's closure note
says it "covers the whole axis generically rather than the three sites currently
known." It does not. It covers one _name family_ generically. Any declaration
that lands after its use and is not called `__mimz_sub_N` is invisible to it.

**(b) BUG-66's fix has a wrong safety argument, and that is the actual defect.**
`bugs/bug-61-70.md` justifies `pre_decl_hoist_pos` as _"safe because every
signal the three sites below can reference is already declared by then."_
Instance output wires are not. They are declared _by_ `emit_instances`, which
runs inside the window. The argument holds for ports and parameters — which is
all BUG-66's own three reproductions touch — and fails for the one signal class
the window itself introduces.

**(c) The fix made this class harder to see, not easier.** Before item 3, this
same source produced an out-of-order `__mimz_sub_N` and the new invariant caught
it (I confirmed: `nc1.mimz` panics under the reverted build, naming
`__mimz_sub_1`). After item 3, the hoisted name is in order and an ordinary wire
is not — so the invariant passes and `mimz compile` exits 0 on Verilog Icarus
refuses. That is a strictly worse detectability property for the axis the
invariant was written to watch.

**Fix shape for BUG-70.** Not another buffer. `emit_instances` must stop writing
straight into `self.out`: render the instance block into a local `String`, and
splice the pre-declaration hoist buffer between _all_ instance output-wire
declarations and the first instantiation line. Equivalently — and smaller —
hoist the output-wire declaration loop out of the per-instance body into its own
pass ahead of `pre_decl_hoist_pos`, which restores the safety argument the
record already claims.

**And widen the invariant, or stop claiming the axis.** Two honest options:

- Check _every_ identifier, not just `__mimz_*`: collect each `wire`/`reg`
  declaration name in the module body and assert no line references one before
  its declaration line. That is the axis. It is maybe fifteen lines more than
  what is there, and it would have caught BUG-70 the moment item 3 landed.
- Or keep it as-is and rewrite GAP-18's closure note to say what it actually
  covers, and reopen the axis as a live gap.

I would take the first. The second is defensible only if the RC's known-issues
list names it.

### 2.4 Release behaviour of the invariant

`debug_assert!` is **live in release** here (`[profile.release] debug-assertions
= true`, deliberate and documented, `Cargo.toml`). So this invariant, if ever
violated in a shipped binary, aborts `mimz compile` with a Rust panic and a
backtrace note — precisely the failure mode item 2 was written to eliminate for
`hoist_unresolved`, ten lines away, on the same day.

That inconsistency should be resolved deliberately rather than by accident.
Item 2's own reasoning applies verbatim: it is a compiler-internal invariant
violation, the user has done nothing wrong, and a `Diag` plus a non-zero exit is
strictly better than an abort. The `cfg!(test)` gate item 2 introduced is
directly reusable. **Not release-blocking on its own** (item 2 already covers
the `None`-branch risk, and this branch has no known live trigger now that
BUG-70 is identified) — but it is the same bug pattern, one function apart, and
should not ship un-noted.

### 3.2 Goldens — changed, but not by a moved hoist

Check 3 expected goldens "unchanged except where a moved hoist legitimately
reorders emitted text." **No golden contains a reordered hoist.** All 33
regenerated fixtures changed by exactly one substitution:

```diff
-    initial value = 0;
+    initial #0 value = 0;
```

Verified mechanically across the whole golden diff of `dfafccd`: every `+`/`-`
pair is an `initial …` line gaining `#0`. Zero value changes, zero reordering.
That is consistent with round 7's finding that no shipped design reaches
BUG-66's three sites — which is also why the goldens could not have shown a
reorder.

**But this is a sixth change, and it is not a reordering.** The `#0` is a
scheduling change to _every_ register and memory power-on seed in every emitted
design. It is well-reasoned in the code (the hoisted operand's continuous
`assign` and the `initial` seed both schedule in time-0's active region with no
ordering guarantee) and it is honestly recorded in BUG-66's status update. I
have one substantive concern with it:

**`initial #0` may not survive FPGA synthesis the way plain `initial` does.**
BUG-65's entire fix depends on the emitted `initial` being honoured as a
power-on value by FPGA flows (the emitted comment says "simulation/FPGA-only",
ASIC excluded). Vivado and Quartus both honour a delay-free
`initial reg = value;` as a power-on state; a delay control inside an `initial`
block is a different construct, and the common behaviour is to warn and ignore —
which would silently drop the initialisation on real FPGA hardware while every
simulation stays green. I have not verified this against a synthesis tool (none
in this environment), so I am flagging it as **unverified risk, not a finding**.
It is cheap to remove the risk: emit the `#0` only when the seed's right-hand
side actually references a hoisted wire — which for the entire shipped corpus is
never, so all 33 goldens would revert to their pre-`dfafccd` text.

### BUG-71 (HIGH) — `emit_testbench` never folds file-level consts into its own env

Pre-existing, known, deliberately deferred, never filed. Two symptoms:

**(a) A testbench that cannot elaborate.** BUG-68's own reproduction, unchanged
at HEAD (Part 1, item 5).

**(b) A testbench that elaborates and reports the wrong verdict.** This one is
worse and is not documented anywhere:

```mimz
const ON: int = 1
module F {
  in a: bits[8]
  const if (ON == 1) { out y: bits[8] } else { out y: bits[4] }
  y = a
}
test "t" for F { a = 0b10101010  expect y == 0b10101010 }
```

```console
$ mimz test ci8.mimz
1 passed, 0 failed
$ mimz compile ci8.mimz -o ci8.v --emit-testbench     # exit 0
$ grep 'output wire' ci8.v ;  grep 'wire \[' ci8_tb.v
    output wire [(8)-1:0] y                # DUT
  wire [4-1:0] y;                          # testbench
$ iverilog -g2005 -o ci8.out ci8.v ci8_tb.v
ci8_tb.v:7: warning: Port 2 (y) of module F expects 8 bit(s), given 4.
$ vvp ci8.out
FAIL: expect (y == 'b10101010) failed
```

`mimz test` PASS, the emitted testbench FAIL, on the same source, with the
emitted DUT correct in both cases. The testbench is modelling a different module
than the one beside it, because `unwrap_or(0)` turns "I cannot evaluate this
condition" into "this condition is false" without a diagnostic.

**Fix shape.** Two parts, both small. Seed `emit_testbench`'s env from the DUT's
own file consts before overlaying `test_env` — `resolve_module_with_file`
already hands back `dut_file`, and `emit()`'s `eval_consts` call is directly
reusable. And separately: `flatten_items`' `.unwrap_or(0)` should not silently
choose a branch on an evaluation error. Push the `Diag`. A `const if` whose
condition cannot be evaluated is a compiler bug or a checker gap, and in either
case is not "false."

The second half of that is worth doing regardless of the first, because it is
the reason this was a silent wrong branch rather than an error message.

## Part 8 — The structural finding

**1. The instrument was built on the right axis and scoped to the wrong noun.**
Round 7's central recommendation was a post-emission invariant, and the
implementation is a faithful, well-tested version of the sentence GAP-18 wrote
down — _no `__mimz_sub_N` may be referenced before its declaration_. The axis
GAP-18 was actually about is _no declaration may land after its use_. One is a
statement about a name family; the other is a statement about the emitted text.
Nobody noticed the substitution because the three known reproductions could not
tell them apart. My first construction that could, did.

**2. The failure migrated again — but this time it stayed inside the same
round.** Rounds 1→6 migrated across rounds: wrong arm → missing arm → call-site
fail-open → which `decls` is in scope → when is the buffer flushed. Round 7's
fix for "when is the buffer flushed" produced "flushed **before the declarations
the window itself emits**," and that happened between one commit and the review
of that commit. The interval is shrinking, which is what convergence looks like
from the inside, but the mechanism has not changed: **a positional invariant is
being maintained by hand in an emitter that has no model of what it has already
declared.**

**3. Three consecutive fixes in one region each produced the next defect.**
BUG-65's fix added the `reg`-reset render above `hoist_pos` → BUG-66. BUG-66's
fix moved the splice above `emit_instances` → BUG-70. That is not carelessness;
each fix's safety argument was written down and each was correct about the
signals its own reproductions touched. It is what happens when correctness is a
property of _where a string is spliced_ rather than of a data structure. GAP-1's
argument, for the fourth round running: a typed elaborated IR has no splice
point, because a hoisted node is a node.

**4. The width family did not grow, and that is the real news.** Thirty-four
instances across seven rounds, and round 8 adds zero. BUG-70 is declaration
order; BUG-71 is a const environment. For the first time the defects found are
in different families than the one the series was named after, and both of them
are _structural_ — they are about what the emitter knows about its own output,
not about what any classifier arm computes. The instruments round 6 and round 7
built are why: the width axis now has two runtime checks on it, and the
remaining surface is somewhere else.

**5. The bug ledger disagreed with a reproduction, and that is worse than the
bug.** BUG-68 is marked FIXED. Its own entry prints a reproduction. The
reproduction fails at HEAD. The residual is described accurately three
paragraphs down, and then explicitly _not filed_. Every prior round in this
series could be reconstructed from the audit trail; this is the first time the
trail says something a five-second check contradicts. It is a one-line
correction (Task 6 of the round-8 plan), and it matters out of proportion to its
size, because seven rounds of credibility rest on those status lines being
literally true.

**6. Tests written around a failing reproduction are the mechanism that let it
through.** `tests/self_determined_regression.rs` uses `const if (1 == 1)`
because the filed repro's `const if (BIG == 1)` "hits a separate, pre-existing
gap this task doesn't touch." The reasoning is sound and the comment is honest.
The consequence is that the shipped regression suite proves the fix works on a
case the bug was not filed against, and is green while the filed case fails. The
rule that prevents this is one sentence: **the test that closes a bug is the
bug's own reproduction, or the bug is not closed.**

### Can `v0.2.0-rc1` be skipped, and `v0.2.0` shipped directly?

Asked directly, so answered directly: **yes — conditionally, and the condition
is evidence, not a label.**

**The case for skipping the RC.** An RC only earns its name if something happens
during it that cannot happen after: a soak period with real users reporting real
designs. This project has no such population today. Without one, `-rc1` is a
version string that delays the same artifact by a release cycle and collects no
information. And the round's own numbers argue the artifact is ready in the way
that matters: 226/226 corpus files elaborate and simulate, 90/90 testbench
modules PASS, gate 5 clean at 5000/5000, and — for the first time in eight
rounds — **no new instance of the width-rule family** (Part 0, row 5). Every
defect still standing is reviewer-constructed, and both new ones are in
different families than the one this series has been chasing.

**The case against.** Three consecutive fixes in this one code region each
spawned the next defect: BUG-65's fix created BUG-66, BUG-66's fix created
BUG-70. The BUG-70 fix is the third in that chain and is structurally the
largest of them — it changes how `emit_instances` writes output and regenerates
goldens again. A first stable release should not _be_ that change.

**The resolution: make the instrument own the axis, then ship 0.2.0.** The
difference between "we fixed three sites" and "the class is closed" is whether
anything watches it when the reviewer stops looking — which is exactly the
argument the round-8 suggestion memo used to justify stopping. Three
conditions, all in the round-8 plan, all small:

1. **Task 1** — BUG-70 fixed.
2. **Task 2** — the declaration-order invariant widened to **every** declared
   identifier in the module body, not just `__mimz_*`. This is the one that
   converts three fixed sites into a watched axis. Without it, skipping the RC
   means shipping a stable release whose headline invariant does not cover what
   its own gap entry says it covers.
3. **Task 4** — the corpus elaboration sweep from Appendix B.2 becomes an
   in-repo test, so the axis is watched corpus-wide on every CI run and not only
   at module-emit time.

With 1–3 landed and the four checks re-run clean: **ship `v0.2.0` directly.** Do
not ship an RC first — there is nothing an RC would find that those three do not
already watch for.

With 1 and 3 landed but **not** 2 — that is, BUG-70 patched while the invariant
stays name-specific — **ship `v0.2.0-rc1`**, because at that point the reviewer
still owns the axis and the next instance is found by a user rather than by the
compiler.

Three things carry over unchanged either way:

- **The withheld claim stays withheld.** "The compiler produces Verilog that
  matches its own type system" is not true until GAP-1 lands, at 0.2.0 exactly
  as at rc1. The defensible claim the plan drafted is correct and should be used
  verbatim.
- **The known-issues list is required, not optional**, and must now name BUG-71
  (a user writing `const if` plus a `test` is ordinary, and the failure is a
  wrong verdict) and GAP-1.
- **`Cargo.toml` still says `version = "0.1.0"`**, in both the workspace root
  and the crate — every emitted file's header currently reads
  `Generated by mimz 0.1.0`. Whichever tag is chosen, that bump is a real task,
  and `crates/mimz-core/src/version.rs` has a test asserting the banner carries
  `COMPILER_VERSION`, so the edition/banner line needs checking with it.

### On the cadence question the plan actually asked

The plan's real thesis is that seven rounds of full adversarial review had hit
diminishing returns as a discovery method, and that the right move was five
fixes and an RC rather than an eighth sweep. **I think that is right, and this
round supports it rather than undermining it.**

Both new defects came out of the plan's own four checks — one from "try to break
the invariant yourself," one from "reproduce the five fixes verbatim." Neither
came from a sweep. The light-touch round did its job: it found what a five-item
batch got wrong, in an afternoon, without re-auditing anything already settled.
A round 9 shaped like rounds 4–7 would have cost five times as much and would
very likely have found the same two things by a longer road.

The one thing I would change about the cadence going forward is smaller than a
round: **when a fix's own record states a safety argument, the next check should
try to falsify that sentence specifically.** BUG-66's record says "every signal
the three sites below can reference is already declared by then." That sentence,
read adversarially, is BUG-70 — and reading it took a minute, not a sweep.

### A.12 — Checked and found NOT reachable

Recorded so the next round does not re-derive them:

- **A file-level `const` in a port width** (`const W: int = 8` … `in a: bits[W]`)
  is rejected by the checker outright — **E0201**, "`W` is not a compile-time
  constant". That closes the widest version of BUG-71: the missing env can only
  reach the emitted testbench through a `const if` **condition**, never through
  a port width. Parameters, which do reach widths, are already in `test_env`.
- **A `const if` whose condition references a file const always takes the
  `else` branch in the testbench**, never the `then` branch, because
  `.unwrap_or(0)` maps "unevaluable" to false. So BUG-71's divergence is
  one-directional, which is why A.9 has to put the wide port in `then`.

### B.2 — The corpus sweep (Part 3.1)

Deliberately broader than round 7's text scan: it runs full `iverilog`
elaboration on every emitted `.v`, which catches declaration-after-use for
**any** symbol rather than only `__mimz_*` names. This is the check that would
have caught BUG-70 corpus-wide, and Task 4 of the round-8 plan proposes making
it an in-repo test.

```bash
#!/usr/bin/env bash
# Round-8 corpus sweep: compile every shipped .mimz, elaborate the emitted
# .v under real iverilog, and run every emitted testbench under vvp.
REPO=/path/to/min-mozhi
M="$REPO/target/release/mimz"
OUT="$1"; mkdir -p "$OUT"; cd "$OUT" || exit 1
: > compile_fail.txt; : > elab_fail.txt; : > vvp_fail.txt; : > order_fail.txt
n=0; tb=0
while IFS= read -r f; do
  n=$((n+1))
  base=$(echo "$f" | sed 's#/#_#g; s#\.mimz$##')
  d="$OUT/$base"; mkdir -p "$d"
  if ! "$M" compile "$REPO/$f" -o "$d/$base.v" --emit-testbench > "$d/c.log" 2>&1; then
    echo "$f" >> compile_fail.txt; continue
  fi
  python order_check.py "$d/$base.v" >> order_fail.txt 2>/dev/null
  if ! iverilog -g2005 -o "$d/$base.vvp" "$d/$base.v" > "$d/e.log" 2>&1; then
    echo "$f" >> elab_fail.txt; continue
  fi
  tbf="$d/${base}_tb.v"
  if [ -f "$tbf" ]; then
    tb=$((tb+1))
    if ! iverilog -g2005 -o "$d/${base}_tb.vvp" "$d/$base.v" "$tbf" > "$d/etb.log" 2>&1; then
      echo "$f (tb elab)" >> vvp_fail.txt; continue
    fi
    ( cd "$d" && vvp "${base}_tb.vvp" > vvp.log 2>&1 )
    grep -q "FAIL" "$d/vvp.log" && echo "$f (FAIL)" >> vvp_fail.txt
  fi
done < <(cd "$REPO" && find examples demo -name "*.mimz" | sort)
echo "files=$n tb_files=$tb"
```

**Known limitation of this harness, stated because it produced a wrong number
first.** Running one `vvp` job per `_tb.v` undercounts PASS lines: the first
testbench module's `$finish` terminates the whole simulation before the rest
report. Part 3.1's 90/0 figure is therefore the in-repo
`every_emitted_testbench_reports_pass_under_vvp`'s, which builds each module
separately with `-s <module>`. Use that test, not this script, for the
testbench count.

`order_check.py` — round 7's out-of-order detection, per module block:

```python
import re, sys

pat = re.compile(r"\b(__mimz_(?:fn_)?sub_\d+)\b")
for path in sys.argv[1:]:
    txt = open(path, encoding="utf-8", errors="replace").read()
    for blk in re.split(r"^(?=module\s)", txt, flags=re.M):
        decl, lines = {}, blk.splitlines()
        for i, l in enumerate(lines):
            t = l.strip()
            if t.startswith("wire ") or t.startswith("reg "):
                for n in pat.findall(l):
                    if t.rstrip().endswith(n + ";") and n not in decl:
                        decl[n] = i
        for i, l in enumerate(lines):
            for n in pat.findall(l):
                if n in decl and i < decl[n]:
                    print(f"{path}: OUT-OF-ORDER {n} used {i+1} declared {decl[n]+1}")
                elif n not in decl:
                    print(f"{path}: UNDECLARED {n} used {i+1}")
```
