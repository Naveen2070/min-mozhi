## BUG-71 (HIGH, FIXED 2026-08-20) - `emit_testbench` never folds file-level consts into its own env, so every `const if` in a DUT silently takes the `else` branch

**Status:** FIXED 2026-08-20, branch `round8-class-closure`. Found 2026-08-18 by round 8
([`review-2026-08-18.md`](../review-2026-08-18.md), Part 1 item 5 and Part 5).
Pre-existing and known: named in round-7 plan Task 5's own status note and in
[BUG-68](bug-61-70.md)'s status update, both ending "not filed as its own bug
entry." This is that entry.

**What.** `emit()` seeds the emitter with the file's own constants before
emitting modules:

```rust
em.env = file_consts;                   // emit_verilog/mod.rs
```

`emit_testbench` does not. It seeds only the test's own arguments and the DUT's
parameter defaults:

```rust
em.env = test_env.clone();              // testbench.rs - args + params only
```

`flatten_items` evaluates every `const if` condition against `self.env` and maps
failure to false:

```rust
let val = consteval::eval(cond, &self.env)
    .map(|v| v.to_i128_saturating())
    .unwrap_or(0);                      // module/instances.rs
```

So a condition naming a file-level `const` is unevaluable inside
`emit_testbench`, `unwrap_or(0)` reads it as **false**, and the testbench is
built from the `else` branch of a `const if` whose `then` branch is what the DUT
actually contains. No diagnostic is emitted at any point.

**Two symptoms, one cause.**

### (a) A testbench that cannot elaborate

[BUG-68](bug-61-70.md)'s own filed reproduction, unchanged at HEAD after that
bug's fix:

```mimz
const BIG: int = 1
module Fuzz {
  in a: bits[4]
  const if (BIG == 1) {
    out y: bits[4]
  }
  y = a
}
test "t" for Fuzz {
  a = 0b1111
  expect y == 0b1111
}
```

```console
$ mimz check ci3.mimz                      # OK
$ mimz test  ci3.mimz                      # 1 passed, 0 failed
$ mimz compile ci3.mimz -o ci3.v --emit-testbench
compiled ci3.mimz -> ci3.v
compiled ci3.mimz -> ci3_tb.v (testbench)  # exit 0
$ iverilog -g2005 -o ci3.out ci3.v ci3_tb.v
ci3_tb.v:18: error: Unable to bind wire/reg/memory `y' in `t_tb'
ci3_tb.v:18: error: Unable to elaborate condition expression.
2 error(s) during elaboration.
```

The emitted testbench has no `wire y` and no `.y(y)` - the `const if` produced
nothing, so the port was invisible to the port-declaration loop.

The hoisting half of BUG-68 fails the same way, now as a `Diag` rather than a
panic (round-7 plan Task 2 working correctly on top of this unfixed cause):

```console
$ mimz compile ci2.mimz -o ci2.v --emit-testbench     # exit 1
error: cannot determine `(y)`'s width here - GAP-16: … at `Unary reduction
operand` (rendered as `(y)`) …
```

**Control that isolates the cause.** Identical source with a literal condition
passes, which is what proves the residual failure is the environment and not
`flatten_items`:

```mimz
module Fuzz {
  in a: bits[4]
  const if (1 == 1) {
    out y: bits[4]
  }
  y = a
}
test "t" for Fuzz { a = 0b1111  expect y == 0b1111 }
```

```console
$ iverilog -g2005 -o ci4.out ci4.v ci4_tb.v && vvp ci4.out
PASS
```

### (b) A testbench that elaborates and reports the opposite verdict

Worse, and not documented anywhere before this entry. When the `else` branch
declares the same port at a different width, the testbench elaborates against a
DUT it is not modelling:

```mimz
const ON: int = 1
module F {
  in a: bits[8]
  const if (ON == 1) {
    out y: bits[8]
  } else {
    out y: bits[4]
  }
  y = a
}
test "t" for F {
  a = 0b10101010
  expect y == 0b10101010
}
```

```console
$ mimz test ci8.mimz
1 passed, 0 failed
$ mimz compile ci8.mimz -o ci8.v --emit-testbench     # exit 0
$ grep 'output wire' ci8.v ;  grep 'wire \[' ci8_tb.v
    output wire [(8)-1:0] y                # DUT - the `then` branch
  wire [4-1:0] y;                          # testbench - the `else` branch
$ iverilog -g2005 -o ci8.out ci8.v ci8_tb.v
ci8_tb.v:7: warning: Port 2 (y) of module F expects 8 bit(s), given 4.
$ vvp ci8.out
FAIL: expect (y == 'b10101010) failed
```

`mimz test` PASS, the emitted testbench FAIL, same source, with the emitted DUT
correct in both cases. The only signal in between is an Icarus port-width
warning.

**This is the one silent path at HEAD.** The emitted hardware is right; what is
wrong is the testbench's verdict about it. Round 8 checked the plan's
"nothing at HEAD is silent wrong hardware" claim explicitly and it survives -
but "nothing is silent" does not.

**Direction of the divergence is one-way.** `.unwrap_or(0)` always chooses
`else`, so the testbench can only ever be built from the branch the DUT did not
take when the condition is true. That is why (b) needs the wide port in `then`.

**Not reachable through port widths.** A file-level `const` cannot appear in a
port width at all - the checker rejects it with **E0201**, "`W` is not a
compile-time constant". Parameters, which can, are already in `test_env`. So the
missing environment reaches the emitted testbench only through a `const if`
condition.

**Reachability.** No shipped example hits it: no `examples/` or `demo/` design
combines a `const if`-generated declaration with a `test` block, and all 90
emitted testbench modules PASS under real `vvp` (round 8, Part 3.1). But
`const if` plus a `test` is ordinary source for a parameterised design, and (b)
fails as a wrong answer rather than as an error.

**Fix.** Two parts, independent, both small.

1. Seed `emit_testbench`'s env from the DUT's own file consts before overlaying
   `test_env`. `resolve_module_with_file` already returns `dut_file`, and
   `emit()`'s `eval_consts` call over `TopItem::Const` is directly reusable.
   Overlay order matters: file consts first, then `test_env`, so an explicit
   test argument still wins.
2. Make `flatten_items` push a `Diag` instead of `.unwrap_or(0)`. A `const if`
   whose condition cannot be evaluated is a compiler bug or a checker gap, and
   in neither case is it "false". Worth doing even if (1) lands first - it is
   what turns this class from a silent wrong branch into a message, the same
   principle round-7 plan Task 2 applied to `hoist_unresolved`.

**Also correct [BUG-68](bug-61-70.md)'s status**, which reads FIXED above a
reproduction that fails, and restore that bug's own regression tests to the
file-level `const` form. Round-8 plan Task 3 and Task 6.

**Category** (round-4 taxonomy): **data source under-populated** (the env), with
a **fail-open call site** (`unwrap_or(0)`) turning it from an error into a wrong
answer - the same pairing as BUG-62, one subsystem over.

**Fix applied 2026-08-20.** Both parts, plus the same fix extended to a third
call site found while making it:

1. `emit_testbench` (`testbench.rs`) now seeds its env from the DUT's own
   file consts, THEN its module-level consts (`em.eval_consts_items(&dut.items,
dut_file_consts)` - the same fold `module()` does for a directly-compiled
   module), before resolving test args/parameter defaults on top. `resolve_module_with_file`
   already returns `dut_file`; `emit_testbench` gained a `files: &[File]`
   parameter (mirroring `emit()`'s own signature) since `Project` itself
   never retained the raw file list - it discards `TopItem::Const` entirely
   building its module/enum/bundle/func tables. Both call sites
   (`src/commands/compile.rs`, the crate's own test helper) updated.
2. `flatten_items` now pushes `consteval::eval`'s own `Diag` (`Result<_, Diag>`,
   directly reusable, same convention `eval_consts` already uses) instead of
   `.unwrap_or(0)` - needed `&mut self` (was `&self`).
3. **Found while wiring (2) in**: `eval_consts_items` - module-level const
   folding, which `emit_testbench` now calls for the first time - had the
   IDENTICAL `unwrap_or(0)`-is-silently-false gap, one function over. Fixed
   the same way and widened from `pub(super)` to `pub(in crate::emit_verilog)`
   so `testbench.rs` (a sibling module) can call it. Deliberately NOT applied
   to `declare_instance_outputs`/`emit_instances`'s own, still-`unwrap_or(0)`
   const-if evaluation (`module/instances.rs`) - those run AFTER
   `flatten_items` on the SAME raw items and would only re-diagnose the
   identical already-reported failure a second (and third) time; the
   compile already fails from `flatten_items`'s own `Diag`, so diagnosing
   there too is pure noise, the same "don't double-report" reasoning
   `declare_instance_outputs`'s own doc comment already gives for unknown-
   module resolution.

**Verified.** All three review repros (port declaration, hoisting `expect`,
width-divergence) now compile, elaborate under real Icarus, and PASS -
agreeing with `mimz test`'s own verdict. BUG-68's status corrected to FIXED
truthfully (its own two reproductions now pass for real, not just the
literal-condition control). 4 tests added:
`bug_71_file_level_const_if_port_is_declared_and_connected_in_the_emitted_testbench`,
`bug_71_file_level_const_if_hoisting_expect_matches_icarus`,
`bug_71_const_if_branch_width_divergence_agrees_with_mimz_test`
(`tests/self_determined_regression.rs`, alongside the `bug_68_*` literal-
condition controls, unchanged), and
`bug_71_unevaluable_const_if_condition_is_a_diagnostic_not_a_silent_else`
(`crates/mimz-core/src/emit_verilog/tests/consts_scoping.rs` - a checker-
bypassing unit test pinning `flatten_items`'s own defensive behavior
directly, since a real, checker-accepted-yet-still-unevaluable condition
could not be constructed post-fix: `const if` cannot reference the
enclosing module's own parameter (E0811), and mimz has no division
operator to force a runtime eval failure another way). One pre-existing
test repointed: `task2_unresolvable_concat_member_is_a_diagnostic_not_a_panic`
used BUG-68's own repro to exercise `hoist_unresolved`'s fallback - this fix
makes that repro resolve correctly and compile clean, so (per that test's
own doc comment, which predicted exactly this churn) it now targets
[BUG-72](#bug-72-medium-fixed-2026-08-20---truncx-symbolic-width-has-no-explicit-narrow-fallback-so-any-self-determined-position-wrapping-it-refuses-to-compile),
still open at the time this task landed (fixed in round-8 plan Task 10,
see BUG-72's own entry below - this test has since moved on to BUG-74).
Full workspace green:
**1307/1307** (`MIMZ_REQUIRE_WASM=1 REQUIRE_IVERILOG=1 cargo test
--workspace`, wasm pkg rebuilt), `cargo fmt`/`clippy -D warnings` clean.

## BUG-72 (MEDIUM, FIXED 2026-08-20) - `trunc(x, <symbolic width>)` has no explicit-narrow fallback, so any self-determined position wrapping it refuses to compile

**Status:** FIXED 2026-08-20 (round-8 plan Task 10). Found 2026-08-19, triaged from a CI fuzz-job crash report
(`pretty_roundtrip`, libFuzzer, `MS: 1 ChangeASCIIInt-`) against a mutated
`shift_register.mimz` - `sr <- &trunc(sr << 1, WIDTH) | extend(din, WIDTH)`.
The crash artifact itself is **stale**: it panicked through
`hoist_unresolved`'s bare `debug_assert!`, the exact failure mode round-7 plan
Task 2 removed (`cfg!(test)` gate, [BUG-67/68](bug-61-70.md)). Reproduced the
identical shape at HEAD on both `target/debug/mimz` and `target/release/mimz`
(neither is a `cargo test` binary, so `cfg!(test)` is false in both, matching
the fuzz binary) - **no panic either time**, only a clean `Diag` and exit 1.
Item 2 holds. What survives the retest is a distinct, currently-open gap one
level down.

**What.** `extend(x, W)` and `trunc(x, W)` are checker-symmetric: both accept
`W` as any compile-time-constant expression, including a module `int`
parameter (`checker/widths/ops/builtins.rs`, the shared `Extend | Trunc` arm,
`eval_width`). The emitter is not symmetric. `kinds::infer_call`'s own
`Extend | Trunc` arm requires `const_fold(&args[1])` - literal integers
only, not a parameter reference:

```rust
Builtin::Extend | Builtin::Trunc => {
    let n = const_fold(&args[1])?;   // kinds.rs - Int literal only
    ...
}
```

so `infer_kind` returns `None` for `trunc(x, WIDTH)` whenever `WIDTH` is
symbolic, same as for `extend`. But every self-determined-position call site
in `expr.rs` (`Unary` reduction operand, concat/replicate member, `$signed`/
`$unsigned`/encoding operand, `nand`/`nor`/`xnor` operand - 8 call sites, all
via `try_widen_symbolic_extend`) recovers from that `None` **only when the
wrapped call is `Builtin::Extend`**:

```rust
let ExprKind::Call { func: Builtin::Extend, args } = &expr.kind else {
    return None;                     // expr.rs:156-162 - Trunc falls through
};
```

`Builtin::Trunc` has no equivalent, so it always falls through to
`hoist_unresolved`, which (post round-7 Task 2) now diagnoses cleanly instead
of aborting - but a checker-accepted, otherwise-ordinary parameterized design
still cannot be compiled.

**Repro**, the shipped `examples/english/shift_register.mimz` with a `&`
prepended to make the `trunc` a reduction operand (`WIDTH` left at its
default so the base case is exercised, not an edge width):

```mimz
module ShiftRegister(WIDTH: int = 1) {
  clock clk
  reset rst
  in  din:  bit
  out dout: bits[WIDTH]
  reg sr: bits[WIDTH] = 0
  on rise(clk) {
    sr <- &trunc(sr << 1, WIDTH) | extend(din, WIDTH)
  }
  dout = sr
}
```

```console
$ mimz check bug72.mimz
OK: bug72.mimz - 1 module(s), 0 test(s), 1 file(s)
$ mimz compile bug72.mimz -o bug72.v      # release AND debug binary, identical
error: cannot determine `__mimz_sub_1[(WIDTH)-1:0]`'s width here - GAP-16:
hoist_unresolved: `infer_kind` returned None for … Call { func: Trunc, args:
[…Binary { op: Shl, lhs: Ident("sr"), … }, Ident("WIDTH")] } at `Unary
reduction operand` … - a hoist site may not silently do nothing when it
cannot resolve a Kind.
$ echo $?
1
```

`mimz check` OK, `mimz compile` refuses on both binaries/profiles - loud, not
silent, not a panic. The unshipped `extend(din, WIDTH)` half of the very same
line compiles fine (`try_widen_symbolic_extend` covers it); only the `trunc`
half is unreachable this way.

**Reachability.** Same self-determined-position family as
[BUG-60](bug-51-60.md) (reduction operand) and
[BUG-46](bug-41-50.md)/[BUG-36](bug-31-40.md) (`trunc`'s own part-select
grammar) - all 8 `try_widen_symbolic_extend` call sites are affected the same
way for a symbolic-width `trunc`, not only the reduction operand shown above:
a concat member (`{a, trunc(x << 1, WIDTH)}`), a replicate member, a
`$signed`/`$unsigned` cast operand, an `encoding()` operand, and a `nand`/
`nor`/`xnor` operand all hit the identical fallthrough. No shipped example
reaches any of them - `shift_register.mimz` uses the un-reduced form, which
`extend`'s own fallback already covers via the OTHER operand on the same
line. Not found by gate 5 either, for the same structural reason
[GAP-20](../gaps.md) already gives for BUG-66/70: the fuzz generator does not
synthesize a `trunc(_, <module parameter>)` shape in a self-determined
position.

**Fix shape - simpler than Extend's own fix, because the target logic
already exists and already handles a symbolic width.** The ORDINARY (not
self-determined) `Builtin::Trunc` render arm (`expr.rs`, ~line 1222) never
const-folds its width argument at all - it substitutes the width expression
as TEXT, unconditionally:

```rust
let n = self.expr_subst(&args[1], subst, arrays);   // symbolic or literal, either way
let sel = format!("{x}[({n})-1:0]");                // Verilog: a parameter IS a legal
                                                     // constant part-select bound
```

(plus the base hoist and the `$signed(...)` wrap for a signed base, both
already there). This is exactly why `extend(din, WIDTH)` on the very same
source line compiles fine and `trunc(sr << 1, WIDTH)` does not when reduced:
the ordinary Trunc arm was never asked to `const_fold` the width in the first
place, only `infer_call`'s `Kind`-producing path was (because a `Kind`'s
`width` field is a concrete `u32`, and a module parameter can't fold to one).

So the fix is not a new width formula - it's giving `try_widen_symbolic_extend`
(or a sibling helper) a `Builtin::Trunc` arm that calls the SAME
hoist-base + `x[(n)-1:0]` + signed-wrap logic the ordinary arm already runs,
instead of trying to route through `infer_kind`/`Kind` at all. Reuses tested
code; no new arithmetic to get wrong. Still needs its own differential (not
just an elaboration check) - the part-select's runtime VALUE must match
`mimz test`'s kernel for a `W` that actually narrows, since a reduction over
the wrong slice width is exactly the shape this project's width bugs hide in.

**Category** (round-4 taxonomy): **classifier arm asymmetry** - `extend`
and `trunc` are one shared checker rule and two independent emitter
fallbacks, and only one of the two was given the symbolic-width case. Same
shape as BUG-46, one layer up (that one was the base-hoist side of `trunc`;
this is the width-argument side).

**Fixed 2026-08-20, branch `round8-class-closure`.** Exactly the fix shape
this entry already gave, and simpler than even that: `try_widen_symbolic_
extend` (`expr.rs`) gained a `Builtin::Trunc` arm, but it needs no
duplicated hoist-base + part-select + signed-wrap logic at all. Every one
of the 8 self-determined-position call sites already computes `text` (via
`render_shift_ctx_operand`, which dispatches through the ORDINARY
`Builtin::Trunc` render arm) BEFORE ever calling this function - and that
ordinary rendering (`x[(n)-1:0]`) is already the self-determined-position
answer too, since a Verilog part-select's own width is always exactly `n`
bits by construction, in ANY position, unlike `extend`'s ambient-context-
dependent passthrough. So the new arm just returns `text` unchanged
(`Some(text.to_string())`) - reusing the caller's own already-correct
rendering directly, rather than re-deriving it from `args[0]`/`args[1]`
the way `Extend`'s own arm has to. Required widening the function's own
signature to accept that pre-rendered `text`, threaded through at all 8
call sites.

Both named differentials added (`tests/self_determined_regression.rs`):
`bug_72_trunc_symbolic_width_reduction_operand_matches_icarus` (the filed
repro verbatim, `WIDTH`'s own default of 1 kept - `|`'s own width-match
rule, E0402, is why the filed repro used 1 rather than a wider default)
and `bug_72_trunc_symbolic_width_concat_member_matches_icarus` (`WIDTH`
widened to 4, so `sr << 1` genuinely grows past `WIDTH` before `trunc`
narrows it back down - proves the fix isn't coincidentally narrow to the
reduction call site). Both watch-fail-first confirmed: temporarily
disabling the new arm reproduces this entry's own GAP-16 diagnostic
exactly, on both tests, restoring it makes both pass. `mimz test`/kernel
and real Icarus agree on both. The shipped `shift_register.mimz` golden is
unchanged by this fix (its own one-line diff this round is Task 7's `#0`
narrowing, unrelated).

One pre-existing test repointed a third time:
`task2_unresolvable_concat_member_is_a_diagnostic_not_a_panic`
(`tests/self_determined_regression.rs`) used this bug's own repro to keep
`hoist_unresolved`'s post-round-7-Task-2 Diag-not-panic gate covered by a
real, checker-accepted program - this fix makes that repro compile clean,
so it no longer reaches the fallback. Repointed at
[BUG-74](#bug-74-medium-open---an-ifmatch-wrapped-enumconstruct-as-a-self-determined-position-argument-reaches-hoist_unresolveds-fallback)
instead, a distinct, still-open gap in the same family, found and filed
while looking for this test's own next home rather than assumed to still
exist.

## BUG-74 (MEDIUM, OPEN) - an `if`/`match`-wrapped `EnumConstruct` as a self-determined-position argument reaches `hoist_unresolved`'s fallback

**Status:** OPEN. Found 2026-08-20 (round-8 plan Task 10), while retiring
BUG-72's own repro from `task2_unresolvable_concat_member_is_a_diagnostic_
not_a_panic` (that test needed a still-open, checker-accepted repro to keep
exercising `hoist_unresolved`'s post-round-7-Task-2 gate, and BUG-72's own
fix in this same round closed its previous one). Not a new discovery from
scratch - `tests/self_determined_regression.rs`'s own `HOIST_CALL_SITES`
table (the "encoding operand" entry) already described this exact shape as
"a genuinely open, structurally-unreachable-today coverage gap" and
confirmed by hand that it reaches the fallback; this entry is that finding
given a bug number and a permanent regression test, not independently
re-derived.

**What.** `kinds::infer_call`'s `Builtin::Encoding` arm (`kinds.rs`) needs
`infer_kind(&args[0], ...)`'s own width - and `infer_kind`'s `EnumConstruct`
arm is `_ => None` unconditionally, deliberately: `EnumConstruct`'s own
render already explicitly zero-pads to the enum's full tag+payload width
(`expr.rs`), so a BARE `EnumConstruct` argument to `encoding()` never needs
its own `Kind` - the render is self-sufficient. But an `if`/`match`
WRAPPING an `EnumConstruct` in each arm/branch, passed directly as
`encoding()`'s own argument, still needs `infer_kind` to resolve the
`if`/`match` node itself (not the individual `EnumConstruct`s underneath),
and `IfExpr`/`Match` inherit `None` from their own arms the same way any
other unresolvable-child construct does - so `encoding(if cond {
Packet.Ctrl(k) } else { Packet.Data(v) })` reaches `hoist_unresolved`'s
fallback, confirmed live:

```console
$ mimz compile bug74.mimz -o bug74.v
error: cannot determine `(((toggle == 0)) ? ({1'd0, k, 4'd0}) : ({1'd1, v})))`'s
width here - GAP-16: hoist_unresolved: `infer_kind` returned `None` at
`encoding operand` ... - a hoist site may not silently do nothing when it
cannot resolve a Kind.
$ echo $?
1
```

Loud, not silent, not a panic - `hoist_unresolved`'s own round-7 Task 2 fix
holds here too. But a checker-accepted design (an enum-typed signal chosen
by a runtime condition, then encoded to bits - a plausible protocol-framing
shape) cannot be compiled.

**Reachability.** Only through a DIRECT `if`/`match` argument to
`encoding()` - an intermediate named `wire p: Packet = if ... {...}` (as
`matrix_encoding_of_payload_enum_in_concat_matches_icarus`'s own source
uses) short-circuits via `is_plain_identifier` before `infer_kind` is ever
consulted, so that shape is NOT affected and stays a valid control. No
shipped example reaches the direct-argument form. Not found by gate 5:
the fuzz generator's own `gen_special_leaves` never constructs an
`EnumConstruct` at all (a separate, pre-existing structural gap, same
family as [GAP-20](../gaps.md)'s own "fuzz vocabulary" finding).

**Fix shape - not investigated in depth, since this bug was found retiring
a different task's own test rather than through dedicated triage.**
Candidates worth checking before committing to one: (a) give `infer_call`'s
`Encoding` arm a fallback that computes the enum's own tag+payload width
directly from the `Type::Named` id, bypassing `infer_kind(&args[0], ...)`
entirely when `args[0]` is an `IfExpr`/`Match` over `EnumConstruct` arms -
mirrors this round's own BUG-72 fix (reuse the render's own already-correct
answer instead of re-deriving a `Kind`); (b) widen `infer_kind`'s own
`IfExpr`/`Match` arms to recurse into `EnumConstruct` branches specifically
for enum tag+payload width, if that's already computable from the
declared enum type alone. Needs its own differential once a fix direction
is chosen, the same way BUG-72's did.

**Category** (round-4 taxonomy): **structural gap in an exhaustive dispatch**

- `infer_kind`'s own `EnumConstruct => None` rule is locally correct (a bare
  `EnumConstruct` needs no `Kind`) but doesn't compose with `IfExpr`/`Match`'s
  generic "inherit the arm's own Kind" rule, the same shape [BUG-55](bug-51-60.md)
  and [BUG-59](bug-51-60.md) found for a shift hiding inside an `if`/`match`
  branch, one layer over (width propagation vs. Kind resolvability).

## BUG-73 (HIGH, FIXED 2026-08-19) - a bundle-typed `wire`'s per-field flattened name can collide with an existing port/wire/reg, producing a self-referential `assign` and a duplicate-declaration elaboration failure

**Status:** FIXED 2026-08-19, branch `round8-class-closure`. Found 2026-08-19, incidentally, verifying round-8 plan
Task 2's widened declaration-order invariant against the full workspace test
suite - unrelated to hoisting/GAP-18, a different subsystem entirely (bundle
field flattening, `module/mod.rs`'s `ModuleItem::Wire` arm).

**What.** A bundle-typed `wire` flattens to one Verilog wire per field, named
`{wire_name}_{field_name}` (`module/mod.rs:252`,
`self.out.push_str(&format!(" wire {w}{}_{};\n", name.name, fname))`) - with
no check that the resulting name is actually free. If a module ALSO has a
port (or another wire/reg) whose name happens to equal that flattened
string, the emitter declares it a SECOND time and assigns it FROM ITSELF:

```mimz
bundle HasUART { tx: bit, rx: bit }
module M {
  in a_tx: bit
  in a_rx: bit
  out o: bit
  wire a: HasUART = { tx: a_tx, rx: a_rx }
  o = a.tx
}
```

```console
$ mimz check bug73.mimz
OK
$ mimz compile bug73.mimz -o bug73.v      # exit 0
```

```verilog
module M (
    input wire a_tx,
    input wire a_rx,
    output wire o
);
    wire a_tx;
    wire a_rx;
    assign a_tx = a_tx;
    assign a_rx = a_rx;
    assign o = a_tx;
endmodule
```

```console
$ iverilog -g2005 -o bug73.out bug73.v
bug73.v:8: error: 'a_tx' has already been declared in this scope.
bug73.v:1:      : It was declared here as a net.
bug73.v:9: error: 'a_rx' has already been declared in this scope.
bug73.v:2:      : It was declared here as a net.
```

`mimz check` OK, `mimz compile` exit 0, real Icarus refuses - loud, not
silent (the collision produces a duplicate-declaration elaboration error,
not a value that quietly computes wrong). The `wire a: HasUART = { tx: a_tx,
rx: a_rx }` intent - bind the bundle's `tx` field FROM the port `a_tx` - is
also lost entirely: the flattened wire is named the SAME as its own RHS
value, so the emitted `assign a_tx = a_tx;` is a tautology, not the intended
binding. Even if Icarus tolerated the redeclaration, the design would not do
what the source says.

**Root cause.** `{wire_name}_{field_name}` is the SAME flattening convention
used for instance-port auto-wires (`{instance}_{port}`, BUG-53) and bundle
ports/`fn` params - none of these sites check the generated name against
`self.cur_decls`/the module's own port list before emitting it. Ports and
plain `wire`/`reg` declarations happen to rarely share a prefix with a
bundle field by accident, which is presumably why 8 rounds of review and
226/226 shipped examples never hit this - but nothing prevents it, and the
repro above is an entirely ordinary naming choice, not a contrived edge case.

**Reachability.** Not in the shipped corpus (226/226 pass; confirmed by the
existing test suite staying green) - needs a user to pick a wire name whose
`{name}_{field}` flattening matches an existing signal, which no shipped
example does. Found via `crates/mimz-core/src/emit_verilog/tests/bundle_flatten.rs`'s
own existing test fixtures (`bundle_typed_fn_param_flattens_to_per_field_inputs`
et al.), which already construct exactly this shape for an unrelated reason
(testing `fn`-param flattening) - the collision was never itself asserted on.

**Fix applied 2026-08-19.** Option (b) from the fix shape above - diagnose,
don't rename - same shape as BUG-4's own fix for colliding sanitized test
names. New `Emitter::declared_signal_names: HashSet<String>` (reset per
module) and `declare_signal_name(&mut self, name, span) -> bool`
(`emit_verilog/mod.rs`): records a name the first time it's declared;
returns `false` and pushes a `Diag` naming the collision on a repeat,
instead of silently emitting a second `wire`/`reg` line. Wired into every
site that computes a name for something about to be declared, in emission
order (whichever candidate is first claims the name):

1. The header port loop (`module()`, plain ports, clock, reset, and
   per-field bundle ports).
2. The "Declarations" loop (`Wire`/`Reg`/`Mem`, bundle-flattened `Wire`
   fields included).
3. `declare_instance_outputs` (round-8 Task 1's own pre-pass) - instance
   auto-wires, bundle-flattened fields included.

`fn`-body-local declarations (a separate Verilog scope entirely, per round-8
Task 2's own `FunctionSkipState` reasoning) are deliberately NOT checked
against this set - a `fn` parameter's own flattened field legitimately
shadows the module scope.

**Verified.** The repro above: `mimz check` OK, `mimz compile` now exits 1
with `` `a_tx` is declared more than once in this module `` (and the same
for `a_rx`) instead of silently emitting the broken Verilog shown above.
Confirmed the SAME check also catches an instance auto-wire colliding with
an ordinary port (`{instance}_{port}` vs. an unrelated same-named port,
two genuinely distinct mimz identifiers - the checker's own duplicate-name
rule, E0003, does not apply since neither name is reused) - the "instance
outputs share the same exposure" question this entry's own fix-shape
section left open. Three tests added,
`crates/mimz-core/src/emit_verilog/tests/bundle_flatten.rs`:
`bug_73_bundle_wire_field_colliding_with_a_port_is_a_diagnostic_not_invalid_verilog`,
`bug_73_instance_auto_wire_colliding_with_a_port_is_a_diagnostic`,
`bug_73_non_colliding_bundle_wire_still_flattens_normally` (control - proves
the check isn't a false-positive trap on ordinary designs). Four pre-existing
`bundle_flatten.rs`/`structural_match.rs` fixtures had this exact incidental
collision in their own test sources (picked matching names for readability,
not realizing it) - renamed the colliding wire (`a`/`b` → `wa`/`wb`/`hu`/`hs`)
rather than changing what those tests assert. Full workspace green:
**1303/1303** (`MIMZ_REQUIRE_WASM=1 REQUIRE_IVERILOG=1 cargo test
--workspace`, wasm pkg rebuilt), `cargo fmt`/`clippy -D warnings` clean.
