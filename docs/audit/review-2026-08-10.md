## Part 3 — New defects

### 3.1 BUG-52 (CRITICAL) — `verilog_self_determined_kind`'s `ExprKind` wildcard: `IfExpr`, `Match` and `Unary` skip the hoist

**Status: OPEN at `359e5db`.**

`self_determined.rs:124` ends `_ => None`. `hoist_if_needed`
(`module/ports.rs:497`) reads that as _skip the hoist_:

```rust
let Some(verilog_kind) = verilog_self_determined_kind(expr, decls, &self.env) else {
    return rendered_text;
};
```

So any `ExprKind` not named in that match — `IfExpr`, `Match`, `Unary`,
`Concat`, `Replicate`, `Slice`, `Index`, `Field`, `FnCall` — is declared
"Verilog agrees with mimz here" **without any reasoning having been written or
checked**. Three of those are reachable with a width-mismatched child and are
live silent miscompiles. `mimz check` passes; `mimz eval`/`mimz test` give the
right answer; the emitted Verilog gives a different one.

Four reproductions, all against real `iverilog -g2005` + `vvp`:

| #   | source                                                             | emitted                                            | `mimz eval` | Icarus    |
| --- | ------------------------------------------------------------------ | -------------------------------------------------- | ----------- | --------- |
| A   | `y = { b, if s { extend(a, 8) } else { extend(a, 8) } }`           | `assign y = {b, ((s) ? ((a)) : ((a)))};`           | **2575**    | **175** ✗ |
| B   | `y = { b, match s { true => extend(a,8), false => extend(a,8) } }` | `assign y = {b, (((s == 1'b1)) ? ((a)) : ((a)))};` | **2575**    | **175** ✗ |
| C   | `y = { b, ~extend(a, 8) }`                                         | `assign y = {b, (~(a))};`                          | **2800**    | **160** ✗ |
| D   | `y = {2{ if s { extend(a,8) } else { extend(a,8) } }}`             | `assign y = {2{((s) ? ((a)) : ((a)))}};`           | **3855**    | **255** ✗ |

(`a = 0b1111`, `b = 0b1010`, `s = 1`; A/B `out y: bits[12]`, C `bits[12]`,
D `bits[16]`.)

Repro A's wrong emission is the same eight bytes as round 1's BUG-28 Repro A,
round 2's BUG-41 repro ⑤ and round 3's BUG-48 repro 2 — _the extend's padding
bits are never materialized and every field to its left shifts down_. Fourth
consecutive round, fourth distinct AST shape, one unaudited match.

Not affected (verified, so the blast radius is bounded): nested `Concat`
(`{b, {c, extend(a,8)}}` → inner member hoisted, 41743 both sides), nested
`Replicate`, `Slice` base (BUG-20's hoist fires), `FnCall` (the emitted Verilog
`function` declares its own return width, 2575 both sides), plain and array
instance ports (Task 1's fix), comparison operands (both sides context-extend to
the max, so a narrower rendering is benign for `==`).

**Why the existing instruments missed it.** `expr_kind_self_determined_coverage`
marks `Unary` `NotApplicable` on the words _"`self_determined.rs`'s own catch-all
confirms no arm ever differs"_ — a catch-all confirms nothing; it is the absence
of an answer. And its `IfExpr`/`Match` arms cite
`bug_41_if_expr_operand_of_add_in_concat_matches_icarus` and
`shape_match_operand_of_add_in_concat_matches_icarus`, which place the
`if`/`match` as an **operand of `+`** inside a concat — a position where the
enclosing `+` triggers the hoist and masks the defect. Neither test places the
`if`/`match` as the concat member itself. The axis's arm citations are
miscalibrated against the position they claim to cover.

The axis's own doc comment is also now stale in a way that matters here: it
states that _"`kinds::infer_kind`'s real match is NOT wildcard-free over
`ExprKind` (`_ => None` at the end), so nothing else in the compiled program
enforces it."_ Task 3's stretch goal made that false — `infer_kind` **is**
wildcard-free — while leaving the sentence in place and never asking the same
question of `verilog_self_determined_kind`, which is the match the sentence would
have been true about.

**Fix shape** (one arm each, mirroring `Min`/`Max`, which is already the same
ternary rendering):

```rust
ExprKind::IfExpr { then, els, .. } => Some(Kind {
    width: self_determined_operand_width(then, decls, env)?
        .max(self_determined_operand_width(els, decls, env)?),
    signed: infer_kind(expr, decls, env)?.signed,
}),
ExprKind::Match { arms, .. } => /* max over arm values, same shape */,
ExprKind::Unary { op, expr: inner } => match op {
    UnOp::RedAnd | UnOp::RedOr | UnOp::RedXor => None, // 1 bit both sides
    _ => Some(Kind { width: self_determined_operand_width(inner, ..)?, .. }),
},
```

**Fix verified, not just proposed.** I applied exactly those three arms, rebuilt
release, and re-ran everything:

| check                                                                | result                                                                                                                                            |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| all four hand repros (A–D)                                           | **fixed** — Icarus now returns 2575 / 2575 / 2800 / 3855, matching `mimz eval`                                                                    |
| the fuzz-found clocked instance (seed 202428078)                     | **fixed** — Icarus 16358, matching the kernel                                                                                                     |
| `REQUIRE_IVERILOG=1 cargo test --workspace --release --no-fail-fast` | **exit 0, 1229 passed / 0 failed** — no regression, including `bug_24_regression_shift_in_if_branch_stays_unhoisted` and the emit-Verilog goldens |
| fuzz at 1000/1000 with the fix                                       | clocked **passes** (was failing at index 449); comb still fails at seed 12649355                                                                  |

That last row is the useful one: it isolates BUG-55 as a genuinely independent

### 3.2 BUG-53 (HIGH) — array-instance `decls` keys are built from the loop counter, not the rendered index

**Status: OPEN at `359e5db`.**

`insert_repeat_instance_output_kinds` (`module/ports.rs:286`) keys every
`repeat`-body instance port as `{inst}__{i}_{port}`, where `i` is the **repeat
loop counter**. `inst_name` (`emit_verilog/mod.rs:678`) renders the instance as
`{inst}__{eval_const(inst.index)}` — the **folded index expression**. And
`emit_instances` (`module/instances.rs:71`) recurses into nested
`Repeat`/`ConstIf`/`ForEach` bodies via `unroll`, while
`insert_repeat_instance_output_kinds` scans only `r.items` for a direct
`ModuleItem::Inst`.

So the keys `infer_kind`'s `Field` arm looks up exist only for the exact shape
Task 1's three repros happened to use: a bare loop variable as the index, one
level deep. Three reproductions, all confirmed against real `iverilog`:

| #   | source                                                                           | emitted                                        | mimz's own type | Icarus    |
| --- | -------------------------------------------------------------------------------- | ---------------------------------------------- | --------------- | --------- |
| A   | `repeat i: 0..1 { let s[i + 1] = Sub(){x:a} }` · `y = { b, s[1].q + a }`         | `assign y = {b, (s__1_q + a)};` — **no hoist** | `bits[9]` → 350 | **174** ✗ |
| B   | `repeat i: 0..1 { repeat j: 0..1 { let s[j] = … } }` · `y = { b, s[0].q + a }`   | `assign y = {b, (s__0_q + a)};` — **no hoist** | 350             | **174** ✗ |
| C   | `repeat i: 0..1 { const if (DEBUG) { let s[i] = … } }` · `y = { b, s[0].q + a }` | `assign y = {b, (s__0_q + a)};` — **no hoist** | 350             | **174** ✗ |

Control case, which is what pins the diagnosis: `repeat i: 1..2 { let s[i] = … }`
reading `s[1].q` — index expression **equals** the loop counter, at a non-zero
base — hoists correctly (`wire [4:0] __mimz_sub_1`) and Icarus agrees at 350. So
`s[1]` is not the problem; the counter-vs-index divergence is.

`examples/english/ripple_adder.mimz` is **not** affected — it writes
`let fa[i]` (bare loop variable, one level) and only the _read_ side uses
`fa[i - 1]`, which folds through `slice_bound_fold` correctly.

**Mitigating, and the reason this is HIGH not CRITICAL:** all three shapes are
unsimulatable, so a user following `check → test → compile` hits a hard error
before the wrong Verilog:

| shape                  | `mimz check` | `mimz sim`                                                          | `mimz compile`        |
| ---------------------- | ------------ | ------------------------------------------------------------------- | --------------------- |
| A (offset index)       | **OK**       | `error: unknown signal s__1_q`                                      | exit 0, wrong Verilog |
| B (nested repeat)      | **OK**       | `error[S0125]: nested repeat is not supported by the simulator yet` | exit 0, wrong Verilog |
| C (const if in repeat) | **OK**       | `error[S0126]: a repeat body may only contain instances and drives` | exit 0, wrong Verilog |

That table is its own finding: three of the compiler's components disagree about
whether these programs exist. Either the checker should reject them (and then A's
`unknown signal` is an internal error leaking to a user), or the simulator and
the emitter should both support them. Today the emitter alone accepts them, and
silently gets them wrong.

### 3.3 BUG-54 (HIGH) — `--emit-testbench`'s `expect` reports PASS on an `x`-valued comparison

**Status: OPEN at `359e5db`.**

`emit_test_stmts` renders an `expect` as:

```verilog
if (!((y == 5))) begin
  $display("FAIL: expect %0s failed", "(y == 5)");
  $finish;
end
$display("PASS");
```

When any operand is `x`/`z`, `y == 5` is `x`, `!(x)` is `x`, and Verilog's `if`
treats `x` as false — so the FAIL branch is skipped and **PASS is printed**. A
design that never resets, never drives an output, or holds `x` for any other
reason passes its own generated testbench.

Reproduced directly: with BUG-51 reintroduced, `y = xxxx` at the expect point,
`(y == 5)` evaluates to `x`, and the emitted testbench prints `PASS`. Same
design with the fix in place prints `PASS` with `y = 0101`. The two outcomes are
indistinguishable from the testbench's verdict.

Note also that BUG-51's own entry in `bugs.md` states the opposite — _"`y == 5`
reads `x == 5`, which is `x` (falsy), so the `expect` **correctly fails** here"_.
It does not. `!(x)` is `x`, `if (x)` is false, the FAIL branch is skipped, and
`PASS` is printed; I ran it. That sentence is the same failure mode as
`expr_kind_self_determined_coverage`'s `Unary` arm — plausible reasoning about
Verilog written down without being executed — this time inside the audit trail
that the rest of this review relies on.

Consequence, and the reason this is worth a HIGH rather than a note:
`emitted_testbench_reset_deassert_does_not_race_the_dut` — the test written
specifically to catch a BUG-51 regression — asserts `contains("PASS")` and
`!contains("FAIL")`, and therefore **cannot fail on that regression**. Task 8's
own load-bearing claim for that test does not hold, and the reason is this bug,
not the test's construction.

**Fix shape:** compare against a known-good form, e.g.
`if ((y === 5) !== 1'b1)` (case-equality, so `x` fails), or emit
`if (^(y) === 1'bx) $display("FAIL: expect … (unknown value)")` alongside. The
`===` form is the smaller change and is legal Verilog-2005.

### 3.4 BUG-55 (CRITICAL) — a signed `>>` inside an `if`/`match` branch escapes BUG-47's context hoist

**Status: OPEN at `359e5db`.** Found by the deep fuzz, comb seed `12649355`
(index 925). Minimized to three lines and confirmed independently:

```mimz
module Fuzz {
  in p0: signed[14]
  in p3: signed[4]
  out y: signed[16]
  y = extend((match unsigned(p3) {
    0 => signed(extend(22, 14))
    1 => signed(extend(22, 14))
    _ => (p0 >> extend(14, 4))
  }), 16)
}
```

```verilog
assign y = ((($unsigned(p3) == 0)) ? ($signed(__mimz_sub_1))
          : ((($unsigned(p3) == 1)) ? ($signed(__mimz_sub_2))
          : ((p0 >> 4'd14))));
```

`p0 = 14429`, `p3 = 2` → the `_` arm. `mimz eval` says **y = 0**; `iverilog` +
`vvp` say **y = 3**.

This is **BUG-47's** defect (a signed `>>` whose left operand Verilog
context-extends to the assignment's width _before_ shifting, so sign bits shift
down into the result) reached through a `match` arm. BUG-47's fix hoists the
shift at the assignment's top level; inside an `if`/`match` branch it never
fires, because `expr.rs` deliberately does **not** treat a branch as
self-determined (`bug_24_regression_shift_in_if_branch_stays_unhoisted` pins that,
correctly — a branch _is_ context-determined) and the classifier's `Match` arm
does not exist to say otherwise.

So the fix is **not** the same as BUG-52's. BUG-52 needs the classifier arm;
BUG-55 needs BUG-47's own signed-`>>` hoist to recurse into `if`/`match`
branches, since the branch inherits the _outer_ context and a `>>` is the one
operator whose value depends on the width it is evaluated at. `bug_47_*`'s four
existing tests all place the shift at the assignment top level; none places it
inside a branch.

### 3.5 GAP-14 (MEDIUM, process) — the release gate is scored at a shallower depth than the project's own CI

Round 3's plan set the per-PR fuzz depth to 400 and, in the same plan (Task 5),
made the 5,000-seed nightly job **daily**. It then scored gate 5 green on the
basis of a 400-seed run. BUG-52 is at clocked index **449** and BUG-55 at comb
index **925** — both outside 400, both well inside 5,000. One night of the CI
this plan shipped would have found both before the gate did.

The pattern is exactly BUG-47's, which round 3 itself recorded: _"BUG-47 was found
at i=642, past the per-PR depth of 400, by a manual gate run."_ Task 5 fixed the
cadence and nobody re-ran the gate at the new cadence's depth. The plan's own
note — _"every deeper run on 2026-08-09 found something"_ — held again on
2026-08-10 and was not tested.

**Fix:** the release gate's own checklist must run at the **nightly** depth
(5000/5000), not the per-PR depth, and gate 5 must not be scorable from a 400-seed
run. This is a one-line change to the gate procedure, not to any code, and it is
the cheapest item in this review.

Two seeds to append to the corpus (`tests/fixtures/fuzz-seeds/`), so neither can
silently come back once fixed:

```text
comb.txt     12649355  # i=925  BUG-55  signed >> inside a match arm escaped BUG-47's context hoist
clocked.txt  202428078  # i=449  BUG-52  if-expression as a concat member skipped the hoist
```

A note in Task 4's favour, since it would be easy to read this section as a
criticism of it: the extended vocabulary is what made both seeds _reachable at
all_. `combine_if`/`combine_match` (`tests/differential_fuzz.rs:992-1006`) are
real combinators over arbitrary generated sub-expressions, not fixed leaves, so
they can and did produce a branch that renders narrower than its mimz width. Round
3's generator could not have emitted either program. Task 4 works; the gate
procedure did not use it.

## Part 4 — The structural finding

Round 3's plan diagnosed the class correctly: reducing two hand-synced matches
to one reduced the _chance_ of missing a case, not the _consequence_. It then
fixed the chance again — exhaustiveness in one match — and left the consequence
untouched in the other. `None` still means "silently skip the hoist" at
`module/ports.rs:497`, reached from a bare `_ => None` at
`self_determined.rs:124`.

Three things follow, and they are what this round would put in front of the team
rather than a fifth bug list.

**1. Exhaustiveness is the wrong invariant on its own.** It catches _variant
addition_. Every instance in this series except BUG-41 was something else:

| round | instance                    | failure mode                                                    |
| ----- | --------------------------- | --------------------------------------------------------------- |
| 1     | BUG-28/29 (`extend`, `abs`) | arm **missing** from the classifier's `Builtin` match           |
| 2     | BUG-41 (5 shapes)           | arm **missing** from the gate's `ExprKind` match                |
| 2     | BUG-42 (`min`/`max`)        | arm **present, reasoning wrong**                                |
| 3     | BUG-48/49 (2 shapes)        | arm **present, too narrow**                                     |
| 3     | BUG-50 (`Replicate`)        | arm **present, wrong width**                                    |
| 3     | BUG-47                      | position **not analyzed at all** (context-determined top level) |
| **4** | **BUG-52** (4 shapes)       | **arm absent, covered by an unaudited wildcard**                |
| **4** | **BUG-53** (3 shapes)       | **arm present; its _data source_ under-populated**              |
| **4** | **BUG-55**                  | **BUG-47's own fix not recursed into `if`/`match` branches**    |

Four of eight are "present but wrong," which no `match` exhaustiveness check can
see. The measurement that proves it is in this review: reverting Task 1's fix
fails five hand-written tests and leaves the exhaustive axis green.

**2. The reasoning at each arm has never been independently audited — and where
it is written down, it is sometimes false.** BUG-42 was the first time an arm's
_reasoning_ was found wrong rather than absent, and `self_determined.rs`'s module
doc now carries the right rule for future arms ("ask _is this argument's RENDERED
width necessarily its mimz width?_, never _is this operator's RESULT width…_").
That rule was never applied backwards to the arms that already existed, and it
was never applied to the `ExprKind` axis at all. Two concrete artefacts of that:
`expr_kind_self_determined_coverage`'s `Unary` arm cites a catch-all as
confirmation, and its `IfExpr`/`Match` arms cite tests for the wrong position.
The axis is a real asset; its contents have the same review status as the code it
was built to police.

**3. This round, for the first time, the project's own instruments beat the
review to it.** BUG-52 and BUG-55 were both found by `differential_fuzz` at the
nightly depth, not by hand-sweeping — BUG-55 I would not have found by inspection
at all, since it needed a signed `>>` inside a `match` arm under a wider
assignment. That is a genuine change in the project's position: three rounds ago
the fuzzer was blind to this whole family, and now it catches instances a
domain-expert sweep misses. What failed this round was not the instrument but the
**procedure that scores the gate** — 400 seeds against a CI configured for 5,000
(GAP-14). That is a much cheaper failure to fix than the previous three, and it
is the single highest-leverage change available here.

**4. The honest closure condition is not "the reported bugs are fixed."** It is
one of:

- **(a)** every arm of **both** matches, on **both** axes, carries a written
  reason that has been checked against real Icarus by someone other than its
  author — a bounded, one-time job of roughly 17 + 14 + 17 + 14 arms, most of
  which are genuinely trivial; or
- **(b)** GAP-1, where the question stops existing because the emitter no longer
  analyses shapes.

Four rounds of "fix the named instances, then harden the surface the named
instances came through" have produced four rounds of new instances. The pattern
is not that the team keeps missing cases; it is that the surface is being audited
one cell at a time by whichever bug arrived last.

## Ship / do-not-ship

**Do not ship v0.2.**

The question this round was asked to answer plainly: _have four independent
rounds now failed to find a further instance of the pattern?_ **No.** Four
independent rounds have each found at least one, including this one, including
after a build-enforced exhaustive match was added specifically to prevent it.
The release-note claim is not supportable, and the bar for it is not "the
reported bugs are fixed" — every round has cleared that bar and none has cleared
this one.

On the specific question the brief raised as a contingency — _if a fifth instance
turns up despite the build-enforced exhaustive match, is exhaustiveness alone
insufficient, and has the reasoning at each arm ever been independently audited?_
— the answers are **yes** and **no**. Exhaustiveness protects against adding a
variant, and four of the seven instances in this series were an arm that was
already there. The reasoning at each arm has never been audited as a body of
work; it has been corrected one arm at a time, by whichever bug arrived last, and
in three places it is currently written down incorrectly.

**The encouraging part is larger this round than in any prior one, and it should
be said plainly.** Two of this round's three new defects were found by the
project's own differential fuzzer, at HEAD, at the depth its own CI is already
configured for — including one (BUG-55) that a domain-expert inspection sweep
missed entirely. Three rounds ago that fuzzer was structurally blind to this
whole family. Task 4 is the item that changed it, and it worked better than its
own acceptance test claims.

So the gap between "shippable" and "not" is now much narrower than the verdict
suggests. It is: run the gate at the depth already configured (minutes), fix
three small arms and one recursion (a day), and audit the remaining ~60 arms once
as a body of work rather than one at a time (a few days). The remaining audit is
bounded, most of it genuinely trivial, and the project already has both
instruments it needs — a differential harness that settles any single arm against
real Icarus in minutes, and an audit trail good enough that the result stays
true. What it has not had, in four rounds, is one pass over all of them instead
of the one that just broke.
