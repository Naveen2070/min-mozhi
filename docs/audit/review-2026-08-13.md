**And the class is still open, for the fifth round running.**

A hand sweep — following round 4's own instruction to check an arm's written
reason against real Icarus _in the position the arm claims to cover_ — produced a
**sixth instance**, with five reproductions:

```text
y = { b, &extend(a, 8) }      a=0b1111, b=0b1010
  emitted     assign y = {b, (&(a))};
  mimz eval   y = 20            iverilog   y = 21          ✗
```

It came through the arm that round-4 plan Task 4 — _the ~60-arm reasoning
audit, the task written specifically to end this series_ — explicitly signed off
as needing no test:

> "The three reductions (RedAnd/RedOr/RedXor) ARE always exactly 1 bit in both
> mimz and Verilog regardless of operand, so no mismatch is possible there and
> **no separate test is needed for that half**."
> — `expr_kind_self_determined_coverage`'s `Unary` arm, HEAD

That sentence answers the **RESULT-width** question. `self_determined.rs`'s own
module doc — written for BUG-42, three rounds ago — says in as many words never
to answer that question:

> "ask _is this argument's RENDERED width necessarily its mimz width?_, never
> _is this operator's RESULT width necessarily its mimz width?_"

The reduction's result width is indeed 1 bit on both sides. Its **operand's
rendered width** is not, and nothing hoists it. This is BUG-42's exact failure
mode, re-committed by the audit that was scoped to find BUG-42's exact failure
mode.

A second, independent defect turned up in the same sweep: `ExprKind::Index`'s
base is never hoisted, so `extend(a,8)[7]` emits `assign y = (a)[7];` —
**unparseable Verilog**, `mimz check` clean, `mimz compile` exit 0. That is
BUG-49's class, reached through the one operand position BUG-20's fix never
covered.

Both are filed here as **BUG-60 (CRITICAL)** and **BUG-61 (HIGH)**.

**Why the instruments did not catch BUG-60, and why that matters more than the
count.** My own gate run at the mandated 5000/5000 depth was **clean** — and so
was the team's. This is not a depth failure like GAP-14; it is a **value-window**
failure. The generator can emit `nand(extend(x, N))`, but zero-extension only
changes an and-reduction when the source operand is **all ones**, which a random
input vector on a 6–14 bit port essentially never is. Depth does not help. This
is the first instance in the series that more fuzzing would not have found, and
it is the strongest argument yet for GAP-1.

## Part 3 — GAP-14: verified as a procedure, and it worked

This was the single most important thing to check, since scoring the gate at the
wrong depth is the exact mistake round 3 made and round 4 caught.

**Does the procedure exist and does it bind?** Yes, as a standing rule, in
[`docs/audit/README.md`](README.md) § "Release-gate scoring convention":

> - Gate 5 is scored at the **nightly depth (5000/5000)**, never the per-PR
>   depth. …
> - Every review's gate table records the **depth the run used** …
> - Prefer dispatching the already-configured `fuzz-nightly` job … over a local run

Round 4's own gate table was retrofitted with a depth column. `ci.yml` still sets
400/400 per-PR (`:86`) and 5000/5000 nightly (`:282`) — the two depths the rule
distinguishes.

**Was gate 5 for this round actually scored at 5000/5000, or was a 400-seed run
reused again?** **Scored at 5000/5000, twice — by the team and independently by
me.** And the team's run is the interesting one:

The procedure landed 2026-08-10 and then **sat unexercised for three days**. The
plan says so in its own words, which is to its credit. When it was finally run
for real on 2026-08-13, it **immediately found a live CRITICAL** — BUG-59, comb
seed `12650993` at fresh index **2563**: past 400, past the 2000 round 4 used,
inside 5000. Fixed the same day (`127dd82`), corpus seed appended, gate re-run
clean (4/4, ~1184 s).

I re-verified the fix myself. `mimz eval` **3072**, Icarus **3072** ✅ (pre-fix:
3072 vs −1024). The emission shows the mechanism — the whole ternary hoisted into
its own 11-bit wire before the outer `<< 3`:

```verilog
wire signed [10:0] __mimz_sub_1;
assign __mimz_sub_1 = ((s) ? ((($signed(4'd12) << 3'd7) >> 3'd2)) : ($signed(11'd1029)));
assign y = (__mimz_sub_1 << 2'd3);
```

I probed the fix's own recursion, since "a fix that doesn't recurse into a nested
position" is one of round 4's three categories and BUG-59's guard is deliberately
narrow (`!allow_shift && matches!(child.kind, IfExpr | Match)`). Wrapping the
same `if` in a unary minus at the shift LHS — `(-(if s { … })) << 3`, a position
the guard does **not** match — still agrees: mimz −3072, Icarus −3072, because
the inner fused chain is hoisted at its own position instead. The scoping holds.

**The corpus.** Both seeds round 4 asked for are present with their exact
annotations, plus BUG-59's:

```text
comb.txt     12649355  # i=925   BUG-55  signed >> inside a match arm escaped BUG-47's context hoist
comb.txt     12650993  # i=2563  BUG-59  fused shift chain in an if-branch, un-hoisted as an outer shift's LHS
clocked.txt  202428078 # i=449   BUG-52  if-expression as a concat member skipped the hoist
```

Replay is unconditional at depth 0 **by construction**, and I checked the
construction rather than the claim: `fuzz_seeds` (`differential_fuzz.rs:86`)
builds `corpus_seeds(kind).into_iter().chain((0..n).map(…))` — `n` (the env var)
gates only the _fresh_ tail; the corpus is prepended unconditionally, and
`corpus_seeds` hard-asserts on an empty parse ("silent data loss"). The property
round 4 verified for the pre-existing corpus holds identically for the three new
entries, because there is no per-entry code path at all.

**Residual, and it is why GAP-14 is closed rather than eliminated.** The rule
lives in prose, in an audit README. Nothing mechanically prevents the next gate
from being scored at 400 — no PR-template line, no CI job, no script. The
project's own three-day gap between writing the rule and running it is the
demonstration. GAP-14 is correctly marked CLOSED (the procedure was followed and
the result recorded, which is the bar it set for itself), but "a rule nobody can
skip" and "a rule someone remembered" are different properties, and this series
has already shown which one survives a handoff.

### 4.2 Was it independent? **No — and it structurally cannot be**

Round 4's closure condition (a) is specific: each arm's reason "has been checked
against real Icarus **by someone other than its original author**." The condition
exists because self-review is what produced BUG-42's wrong reasoning and the
stale doc-comments in the first place.

```console
$ git log --format="%an" | sort | uniq -c | sort -rn
     45 Naveen2070
      5 github-actions[bot]
```

One human author, repo-wide. The same person wrote the arms, wrote the audit,
wrote the coverage docs, and signed off the reasons. Condition (a) is not
partially met; it is **unmeetable as stated** on a single-maintainer project.

I am raising this as [GAP-15](gaps.md) rather than as a criticism, because it is
a structural fact about the project, not a lapse. But it is the reason this round
found a sixth instance in the audited surface within an hour, and it is why the
closure condition needs restating in a form a solo maintainer can actually
satisfy — see Part 8.

### 4.3 Does it hold? **No. Two arms' written reasons are false, and BUG-60 comes straight through one**

I sampled arms the way the brief asked: hand-built cases in the position each arm
**claims** to cover, not the position its cited test happens to use.

**The `Unary` arm — round 4's own flagged arm, corrected in the wrong half.**
Round 4 flagged it for citing `self_determined.rs`'s catch-all as confirmation.
The audit fixed that: it now cites `bug_52_unary_not_of_an_extend_in_a_concat_matches_icarus`
for the **non-reduction** half. But it then wrote a _new_ unchecked claim for the
**reduction** half — "no mismatch is possible there and no separate test is
needed" — reasoning about the **result** width, the question the module doc
forbids. Verified false, five ways: **BUG-60** below.

**The `Nand`/`Nor`/`Xnor` builtin arm — the same claim, and the citation does not
exercise it.** The arm reads "a reduction is exactly 1 bit in both models
**regardless of operand width**, so `None` needs no recursion proof either", and
cites `matrix_nand_in_concat_matches_icarus`. That test is:

```rust
y = { b, nand(a) }      // a: bits[4] — a bare identifier
```

A bare identifier's rendered width **is** its mimz width by definition, so the
test cannot possibly discriminate on "regardless of operand width". This is
precisely the "citation exercises a different position from the claim" gap BUG-52
was filed for, still live, in an arm the audit reviewed and signed off. Swap the
operand for one that renders narrower — `nand(extend(a, 8))` — and the two sides
diverge.

**What this establishes**, and it is the load-bearing finding of the round:
round 4's diagnosis was right, and the remedy it prescribed does not follow from
it. The audit applied the BUG-42 rule to most arms and then, on the two arms
where the operator's _result_ is trivially the same width in both models, slipped
back to the result-width question — because that is the intuitive question, and
there was no second reader to notice. An audit whose only defence against a
reasoning error is the same reasoner does not close a class whose failure mode is
reasoning errors.

## Part 6 — New defects

### 6.1 BUG-60 (CRITICAL) — a reduction's operand is a self-determined position that nothing analyses

**Status: OPEN at `586d0f4`.**

Verilog self-determines a reduction operator's operand at its own width. mimz's
emitter has **no hoist site for it**. `hoist_if_needed` is wired at exactly five
places (`expr.rs:532`/`:539` binary LHS/RHS, `:675` concat members, `:696`
replication members, `:868`/`:882`/`:897` the three recursing `Call` args), and
`hoist_width_effect_operand` — which _is_ called at a `Unary`'s operand — only
fires on a lossless/wrap **arithmetic** child, never on an `extend`. So
`extend(a, 8)` under a reduction renders as the bare `(a)` and the reduction runs
over four bits instead of eight.

The classifier's two arms that should have caught it both answer the wrong
question:

```rust
// self_determined.rs — ExprKind::Unary
UnOp::RedAnd | UnOp::RedOr | UnOp::RedXor => None,     // "1 bit in BOTH models"
// self_determined.rs — ExprKind::Call
Builtin::Trunc | Builtin::Nand | Builtin::Nor | Builtin::Xnor => None,
//   "Reductions are 1-bit on both sides regardless of operand width."
```

Both statements are true about the **result** and irrelevant to the **operand**.

Five reproductions, all `mimz check`-clean, all against real `iverilog -g2005` +
`vvp`, `a = 0b1111`, `b = 0b1010`:

| #   | source                                 | emitted                   | `mimz eval` | Icarus   |
| --- | -------------------------------------- | ------------------------- | ----------- | -------- |
| A   | `y = { b, &extend(a, 8) }` · `bits[5]` | `assign y = {b, (&(a))};` | **20**      | **21** ✗ |
| B   | `y = {3{ &extend(a, 8) }}` · `bits[3]` | `assign y = {3{(&(a))}};` | **0**       | **7** ✗  |
| C   | `y = &extend(a, 8)` · `bit`            | `assign y = (&(a));`      | **0**       | **1** ✗  |
| D   | `y = nand(extend(a, 8))` · `bit`       | `assign y = (~&((a)));`   | **1**       | **0** ✗  |
| E   | `y = \|(~extend(a, 8))` · `bit`        | `assign y = (\|(~(a)));`  | **1**       | **0** ✗  |

**C, D and E are at a plain top-level assignment** — not in a concat, not in a
replication, not in any of the four positions this whole series has been about.
That makes BUG-60 wider than every prior member of the family: the enclosing
context is irrelevant, because the mismatch is entirely inside the operand.

**Which reductions can diverge.** Zero-extension only perturbs an **and**-
reduction (padding zeros force the mimz result to 0 while Verilog reduces the
bare, possibly all-ones operand). `or`/`xor` reductions are unaffected by zero
padding — but `nand` is the negated and-reduction (D), and a `~` between the
extend and the reduction turns the padding into ones, which flips `or` and `xor`
too (E). Sign-extension of a signed operand perturbs all three. So the blast
radius is every reduction form the language has, not just `&`.

**Reachability.** `&a`, `|a`, `^a` are taught in
[`docs/guide/05-operators.md`](../guide/05-operators.md) § Reductions, chapter 5
of the user book — "1 if every bit of a is 1". `&extend(x, N)` is the natural way
a learner asks "are all bits of this widened value set". No shipped example uses
a reduction, which is why the golden suite never saw it.

**Why the fuzzer misses it, and why this one is different from GAP-14.**
`wrap_builtin` (`differential_fuzz.rs:842`) _can_ generate `nand(<any frag>)`
over an `extend`-wrapped fragment, so the **shape** is reachable. But the
divergence needs the source operand to be **all ones**, and the harness drives
random input vectors into 6–14-bit ports. The probability per seed is
vanishing, and it does not improve with depth. My 5000/5000 run was clean; so was
the team's. **This is the first instance in the series that more fuzzing would
not have found.** GAP-14 was "the instrument saw it and the procedure didn't
look"; this is "the instrument is value-blind at this shape". Those want
different fixes — the second one wants GAP-1, or at minimum a value-directed
generator that biases toward all-ones/all-zeros operands.

**Fix shape.** The narrow fix is one hoist site: treat a reduction's operand as
self-determined and hoist it when its rendered width differs from its mimz width,
for both `ExprKind::Unary`'s three reduction ops and `Builtin::Nand`/`Nor`/
`Xnor`'s argument. The classifier arms stay `None` — the _result_ really is 1 bit
— but the operand must be walked. Both coverage docs' reduction reasons must then
be rewritten to answer the operand question, and each needs a differential with a
**narrow-rendering** operand, not a bare identifier.

**Category** (round 4's taxonomy): primarily **position not analysed at all** —
the reduction-operand position, like BUG-47's context-determined top level —
compounded by **arm present, reasoning wrong**, since two arms assert in writing
that this position needs no analysis.

### 6.2 BUG-61 (HIGH) — `ExprKind::Index`'s base is never hoisted: unparseable Verilog

**Status: OPEN at `586d0f4`.**

BUG-20 forces a non-identifier **slice** base to a named wire. Nothing does the
same for a **bit-select** base. Two reproductions:

| source                | emitted                 | `iverilog -g2005`                                        |
| --------------------- | ----------------------- | -------------------------------------------------------- |
| `y = extend(a, 8)[7]` | `assign y = (a)[7];`    | `syntax error` · `Syntax error in continuous assignment` |
| `y = {a, b}[3]`       | `assign y = {a, b}[3];` | `syntax error` · `Syntax error in continuous assignment` |

`mimz check` reports `OK`. `mimz compile` exits **0** and writes the file.
`mimz eval` answers correctly (0 for the first, on `a = 0b1111`), so the kernel
and the checker agree with each other and only the emitter is wrong — the same
shape as BUG-49.

Contrast, which pins the diagnosis: the **slice** form of the identical
expression, `extend(a, 8)[7:4]`, hoists correctly
(`wire … __mimz_sub_1; assign y = __mimz_sub_1[7:4];`) and agrees with Icarus at 0. So the machinery exists and `Index` was never wired into it.

The coverage axis's `Index` arm reads "a bit-select is 1 bit in both models; a
`mem` read renders as the declared element width" and cites
`bug_41_mem_read_operand_of_add_in_concat_matches_icarus` — again a claim about
the **result**, and a citation for the mem-read branch only. The bit-select
branch's **base** is unexamined, in both the code and the audit.

**Severity HIGH, not CRITICAL:** a loud elaboration failure at the Icarus step,
not a silent wrong value — BUG-49's own reasoning.

**Fix shape:** call the existing `hoist_slice_base_if_needed` from
`ExprKind::Index`'s bit-select branch, the same way `ExprKind::Slice` already
does. Small, and the helper is already correct.

**Category:** **a fix that doesn't recurse into a nested position** — BUG-20's
fix, never extended to the sibling node.

## Part 8 — The structural finding

**1. Round 4's diagnosis was right and its remedy does not follow from it.**
Round 4 established that exhaustiveness catches variant addition, not wrong
reasoning, and prescribed a one-time reasoning audit over ~60 arms. The audit was
done, carefully, and produced three new filed bugs and four corrected citations —
and then re-committed the original error on the two arms where the intuitive
question and the correct question diverge most quietly. A reasoning audit whose
only check on a reason is the reasoner is not a different instrument from the
reasoning that produced the arms.

**2. The failure mode has migrated to exactly where the audit's own rules point.**
Task 4 wrote two rules into the axis: _a citation must exercise the position the
arm claims_, and _an arm may not cite the absence of a rule as evidence for the
rule_. BUG-60 violates both, in arms the audit reviewed:
`matrix_nand_in_concat_matches_icarus` cites a bare-identifier operand for a claim
about "regardless of operand width" (rule 1), and the `Unary` reduction half cites
no test at all on the grounds that none is needed (rule 2). **The rules are
correct; they were not applied to the arms that looked obvious.** "Obvious" is
where a solo reviewer's attention is cheapest, which is where a second reader is
worth most.

**3. This is the first instance the fuzzer could not have found.** Every prior
member of this family was a _width_ mismatch — structurally visible, and either
caught by the classifier's check or reachable by any input vector once the shape
was generated. BUG-60 is a _value_ divergence at matching widths, gated on an
all-ones (or all-zeros, after `~`) operand. Depth does not reach it. That changes
what "the instruments are working" means: round 4 could truthfully say the
project's own harness now out-performs a domain-expert sweep. This round, the
sweep found what 10,000 seeds did not.

**4. The count.** Round 3 counted eighteen bugs in the "two implementations of
one width rule disagreed" family; round 4 made it twenty-one. Add BUG-56, 57, 58,
59 (found by the team) and BUG-60, 61 (found here): **twenty-seven**. Six of them
landed _since round 4_, four of those found by the project itself — which is the
encouraging half — and the running cost is unchanged at roughly two CRITICALs per
release-readiness round, five rounds running.

**5. A restated closure condition, since (a) is unmeetable here.** Round 4's
condition (a) requires a second human. This project has one. The honest options
are:

- **(a′) Mechanise the second reader.** Every arm that returns `None` must carry
  a differential whose operand _renders narrower than its mimz width_ — not a
  bare identifier — or an explicit, build-enforced `NotApplicable` reason that
  names a **checker rule or grammar restriction by code**, never a property of
  the operator. That is a mechanical rule a solo maintainer can apply without
  needing to out-think their own intuition, and it is exactly the rule BUG-60 and
  BUG-61 both fail. Roughly a dozen arms currently rest on "no mismatch is
  possible", and each is a candidate.
- **(b) GAP-1.** Unchanged, and now stronger: BUG-60 is the first member of the
  family that neither the classifier's mismatch check nor deeper fuzzing can
  reach, because both are width-based and this one is not.

Five rounds of "fix the named instances, then harden the surface the named
instances came through" have produced five rounds of new instances. The surface is
no longer being audited one cell at a time by whichever bug arrived last — round 4
fixed that, and the audit was real. It is being audited by one person against
their own intuition, and the intuition is wrong in a specific, repeatable place:
whenever the operator's _result_ width is obviously the same on both sides.
